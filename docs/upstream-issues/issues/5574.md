## Aufarbeitung: Supabase-PostgreSQL mit SSL und richtigem Konfigurationspfad starten

**Bereich:** Datenbank / PostgreSQL · **Priorität:** P1 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Supabase-PostgreSQL bindet nach Aktivierung von SSL nur noch auf localhost. Ein Kommentar zeigt, dass der neue Startbefehl die imageeigene -D-Konfiguration verliert. Aktueller Code baut bei SSL ebenfalls einen eigenen postgres-Befehl; die Wirkung hängt vom tatsächlich unterstützten Image ab.

### Reproduktion / Prüfszenario

1. Supabase-PostgreSQL-Testressource zuerst ohne SSL starten und SHOW config_file sowie listen_addresses auslesen.
2. SSL aktivieren und dieselben Werte sowie den effektiven Container-Cmd erneut prüfen.
3. Öffentlichen Datenbankproxy und internen Zugriff vergleichen; Standard-PostgreSQL als Kontrollfall nutzen.

### Befunde

- Kommentar 3024380879 zeigt den Wechsel von postgres -D /etc/postgresql zu einem SSL-Befehl ohne dieses Argument.
- StartPostgresql setzt bei enable_ssl einen expliziten command mit ssl-Parametern.
- Ein config_file-Argument wird nur beim benutzerdefinierten postgres_conf ergänzt.

### Umsetzungsschritte

- [ ] Image-Entrypoint und Default-Cmd der unterstützten Supabase-Variante prüfen.
- [ ] Notwendige imageeigene Konfigurations-/Datenpfade beim Ergänzen von SSL erhalten oder sauber imagespezifisch konfigurieren.
- [ ] Verbindungstest muss nach jeder Einstellungsänderung den tatsächlich geladenen Pfad nachweisen.

### Abnahmekriterien und Regressionstests

- [ ] SSL aktiviert die Verschlüsselung, ohne unbeabsichtigt das Listen-Interface oder Konfigurationsverzeichnis zu wechseln.
- [ ] Berechtigte Clients können sich mit TLS verbinden; unberechtigte bleiben abgewiesen.
- [ ] Standard-PostgreSQL, Supabase und benutzerdefinierte Konfiguration starten mit ihren erwarteten Werten.

### Offene Fragen und Risiken

- Die im Issue erwähnte Abschaltung von SSL ist keine dauerhafte Lösung.
- Alle Interfaces zu öffnen ersetzt keine Netzwerk- und pg_hba-Zugriffsbeschränkung.

````markdown
I have the same (or a similar) issue with the Supabase Postgres version via Coolify. I'm using the cloud version of Coolify (v4.0.0-beta.420.1).

It *does* work as long as I don't change any configuration. As soon as I enable SSL via the checkbox, the database starts, but is bound to `localhost`/`127.0.0.1` instead of all IPs (`0.0.0.0`).

Changing the SSL setting after an initial (correct) start, also changes the bound IP to `127.0.0.1`.

In short, to reproduce:

- Create a new Supabase Database resource
- Enable SSL
- Start the databas
- You should see that it is bound to `127.0.0.1:5432` in the logs
- We would expect it to be bound to `0.0.0.0:5432`, as it is when we don't change the SSL config (maybe others too)

The configuration in the container (after the change) seems to be ok:
```
root@58adcf47ef30:/# cat /etc/postgresql/postgresql.conf | grep listen
listen_addresses = '*'		# what IP address(es) to listen on;
```

But there is a second config file in `/var/lib/postgresql/data/postgresql.conf`
```
root@58adcf47ef30:/# cat /var/lib/postgresql/data/postgresql.conf | grep listen
#listen_addresses = 'localhost'		# what IP address(es) to listen on;
```

The database seems to be loading the second one:
```
root@58adcf47ef30:/# su - postgres -c "psql -c 'SHOW config_file;'"
               config_file
------------------------------------------
 /var/lib/postgresql/data/postgresql.conf
(1 row)
```

I thinke the issue is this:

When I start the database without enabling SSL, it is run like this:
```
/usr/bin/postgres -D /etc/postgresql
```

When I start the database with SSL enabled, it is run like this:
```
/usr/bin/postgres -c ssl=on -c ssl_cert_file=/var/lib/postgresql/certs/server.crt -c ssl_key_file=/var/lib/postgresql/certs/server.key
```

I don't have a workaround besides not enabling SSL. 🤷
````
