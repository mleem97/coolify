# Upstream #9643: Verschlüsselte HTTP-Basic-Auth-Passwörter ohne varchar-Überlauf speichern

## Aufarbeitung: Verschlüsselte HTTP-Basic-Auth-Passwörter ohne varchar-Überlauf speichern

**Bereich:** Datenbankschema / HTTP Basic Auth / Migration · **Priorität:** P1 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Das Passwortfeld für HTTP Basic Auth ist in der produktiven Migration als varchar(255) angelegt, wird im aktuellen Model jedoch verschlüsselt gespeichert. Der Verschlüsselungsumschlag kann diese Grenze bereits bei moderaten Klartextlängen überschreiten. Ein Testschema mit TEXT verdeckt das Risiko, sodass ein echter PostgreSQL-Migrationstest erforderlich ist.

### Reproduktion / Prüfszenario

1. Eine PostgreSQL-Testdatenbank aus der produktiven Migrationshistorie aufbauen und den tatsächlichen Typ von applications.http_basic_auth_password prüfen.
2. Basic Auth über die reguläre Oberfläche mit 31, 32 und einer längeren unterstützten Passwortlänge speichern; anschließend den Wert wieder laden und am Proxy authentisieren.
3. Den Upgradepfad mit bereits gespeicherten verschlüsselten Werten testen und custom_labels-Schemadrift getrennt erfassen.

### Befunde

- Originalmeldung zu beta.473 nennt erfolgreichen 31-Zeichen- und scheiternden 32-Zeichen-Fall; spätere Kommentare melden SQLSTATE 22001 auch unter v4.1.1.
- database/migrations/2025_04_17_110026_add_application_http_basic_auth_fields.php legt http_basic_auth_password weiterhin mit string() an; Application::casts() verwendet dafür encrypted.
- database/schema/testing-schema.sql definiert Passwort, Benutzername und custom_labels dagegen als TEXT. Ein ausschließlich darauf beruhender UI-Test kann die produktive Längenbegrenzung nicht erkennen.
- Der Kommentar über ebenfalls verschlüsselten Benutzernamen trifft auf den geprüften Modelstand nicht zu: aktuell ist nur das Passwort verschlüsselt. Die ursprüngliche custom_labels-Migration verwendet bereits text(), sodass dort gemeldetes varchar ein gesonderter Driftfall ist.
- Ein Kommentar vom 30.10.2026 verlinkt einen Fork-Fix; eine Übernahme dieser Migration ist im untersuchten Stand nicht vorhanden.

### Umsetzungsschritte

- [ ] Eine neue Vorwärtsmigration von http_basic_auth_password auf TEXT ergänzen; vorhandenen Ciphertext unverändert erhalten, statt nur die alte Migration umzuschreiben.
- [ ] Einen PostgreSQL-Test des realen Upgradepfads und einen UI-Speichertest mit einer längeren unterstützten Passwortlänge ergänzen.
- [ ] Validierung und unterstützte Passwortlänge mit den vorhandenen Hashalgorithmen abstimmen; Speicherfehler nicht durch ein künstliches 31-Zeichen-Limit kaschieren.
- [ ] Für einen Rollback keine stille Verkleinerung mit Abschneiden vorhandener Werte vorsehen; custom_labels-Drift separat diagnostizieren.

### Abnahmekriterien und Regressionstests

- [ ] Ein frischer Installationspfad und ein Upgrade vorhandener PostgreSQL-Datenbanken speichern die unterstützten längeren Passwörter ohne SQL-Fehler.
- [ ] Bereits gespeicherte Zugangsdaten bleiben entschlüsselbar und funktionieren am Proxy.
- [ ] Normales Speichern und Aktivieren von Basic Auth erzeugen gültige Labels; Fehlerfälle legen weder Klartext noch Ciphertext offen.
- [ ] Der Test schlägt auf dem bisherigen varchar-Schema tatsächlich fehl und besteht erst mit der neuen Migration.

### Offene Fragen und Risiken

- Die genaue Klartextgrenze hängt vom Verschlüsselungsformat ab; 31/32 ist die beobachtete Grenze der Meldung und kein allgemeiner Vertragswert.
- Die in Kommentaren gemeldete abweichende custom_labels-Spalte ist ohne Einsicht in die betroffene Installation nicht erklärt.
- Keine Produktionsmigration oder Laufzeitänderung wurde vorgenommen.

````markdown
### Error Message and Logs

```
SQLSTATE[22001]: String data, right truncated: 7
ERROR: value too long for type character varying(255)
(Connection: pgsql, Host: coolify-db, Port: 5432, Database: coolify,
 SQL: update "applications"

          "updated_at" = 2026-04-18 22:29:44
      where "id" = <id>)
```

The value stored in `http_basic_auth_password` is Laravel-encrypted (`eyJpdiI6...` format — JSON with IV, ciphertext, MAC, base64-wrapped). The encryption overhead pushes even short passwords past the 255 character column limit. Confirmed by testing: a 31-character password saves successfully, a 32-character password fails with the error above.

### Steps to Reproduce

1. Open any standard application in Coolify.
2. Go to **Configuration → General → HTTP Basic Authentication**.
3. Enable it, set a username, and set a password of 32 characters (e.g. 32 × `a`).
4. Click **Save**.
5. Observe HTTP 500 with the SQL error above.
6. Repeat with 31 characters — saves successfully.
````

````markdown
Confirmando na v4.1.1 + duas colunas a mais no escopo.

  Tropecei nisso num `curl install` recém-feito de v4.1.1 + PostgreSQL 16 (o `coolify-db` empacotado). Ativar **HTTP Basic Authentication** em qualquer Application falha o
   `Save` com:

  ```
  SQLSTATE[22001]: String data, right truncated: 7
  ERROR: value too long for type character varying(255)
  ```

  `Crypt::encrypt()` retorna um envelope `{iv, value, mac, tag}` em base64 — mesmo uma senha curta serializa a ~270 chars. `$table->string()` em [`2025_04_17_110026_add_ap
  plication_http_basic_auth_fields.php`](https://github.com/coollabsio/coolify/blob/main/database/migrations/2025_04_17_110026_add_application_http_basic_auth_fields.php)
  cria `varchar(255)`, então estoura imediatamente.

  Além de `http_basic_auth_password`, outras duas colunas estavam em `varchar(255)` na minha instância e também estouraram no `Save` quando Basic Auth é ativado:

  | Coluna | Tipo atual | Por que estoura |
  | `applications.http_basic_auth_password` | `varchar(255)` | envelope encriptado de ~270+ chars |
  | `applications.http_basic_auth_username` | `varchar(255)` | mesmo caminho de criptografia, mesmo envelope |
  | `applications.custom_labels` | `varchar(255)` na minha instância | Coolify gera ~1.5KB de labels Traefik+Caddy (`http-basic-auth-...` middleware + `caddy_0.basicauth.<user>`) ao ligar Basic Auth |

  > Nota sobre `custom_labels`: a [migration original](https://github.com/coollabsio/coolify/blob/main/database/migrations/2023_10_18_072519_add_custom_labels_applications_table.php) usa `text()`, e o  `testing-schema.sql` também já tem como `TEXT`. Minha instância v4.1.1 ainda mostrava `varchar(255)` — provavelmente drift de upgrade. De qualquer forma, o tipo desejado em produção é `TEXT`.

  ### Workaround (sem restart)

  ```bash
  sudo docker exec coolify-db psql -U coolify -d coolify -c "
  ALTER TABLE applications ALTER COLUMN custom_labels TYPE TEXT;
  ALTER TABLE applications ALTER COLUMN http_basic_auth_password TYPE TEXT;
  ALTER TABLE applications ALTER COLUMN http_basic_auth_username TYPE TEXT;
  "
  ```

  Depois disso o `Save` passa e Basic Auth funciona normal.
````
