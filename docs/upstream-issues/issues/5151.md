## Aufarbeitung: Compose-Datei des PR-Commits für Vorschauen verwenden

**Bereich:** Preview / Compose · **Priorität:** P1 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

PR-Vorschauen bauen den PR-Code, verwenden aber nach Berichten die Compose-Konfiguration des Hauptbranches. Der aktuelle Ladevorgang ruft loadComposeFile ohne PR- oder Commit-Parameter auf; dieser Datenfluss passt zum gemeldeten Problem und benötigt eine isolierte Preview-Konfiguration.

### Reproduktion / Prüfszenario

1. Produktions-Compose und PR-Compose mit eindeutig verschiedenen, harmlosen Service-/Buildmarkern anlegen.
2. PR-Vorschau deployen und finalen Compose-Output mit dem PR-Commit vergleichen.
3. Zwei unterschiedliche PRs parallel sowie einen erneuten Commit auf denselben PR testen.

### Befunde

- Kommentar 5894197209 meldet das Verhalten noch für v4.3.23.
- Kommentar 5895804582 beschreibt Vorschauen zu diesem Zeitpunkt ausdrücklich als Code-/ENV-Änderungen mit aktivem Compose.
- ApplicationDeploymentJob::loadComposeFileForDeployment ruft application->loadComposeFile(isInit: false) ohne Preview-Ref auf; das anschließende Parsing bekommt dagegen die pull_request_id.

### Umsetzungsschritte

- [ ] Compose-Inhalt anhand des tatsächlich ausgecheckten und freigegebenen PR-Commits laden.
- [ ] Preview-Compose getrennt speichern, damit Produktionskonfiguration nicht durch einen PR überschrieben wird.
- [ ] Preview-Berechtigungen, Domains, Volumes und Secrets vor Verwendung geänderter Compose-Dateien prüfen.

### Abnahmekriterien und Regressionstests

- [ ] Preview verwendet nachweislich die Compose-Datei ihres PR-Commits.
- [ ] Zwei PRs und Produktion verändern weder Konfiguration noch Volumes gegenseitig.
- [ ] Nicht freigegebene Fork-Previews können keine geschützten Einstellungen übernehmen.

### Offene Fragen und Risiken

- Compose-Änderungen können privilegierte Container oder Hostmounts definieren; vorhandenes Preview-Vertrauensmodell muss gelten.
- Statische Datenflussprüfung ersetzt keinen tatsächlichen Test-Deploy.
