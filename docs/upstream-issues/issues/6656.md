# Upstream #6656: Speicherspitzen bei gecachten Next.js-Builds messen und begrenzen

[Zur Gesamtübersicht](../README.md)

## Aufarbeitung: Speicherspitzen bei gecachten Next.js-Builds messen und begrenzen

**Bereich:** Build / Next.js / Ressourcen · **Priorität:** P1 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Wiederholte gecachte Next.js-Builds verbrauchen laut Meldung mehrere Gigabyte RAM und beeinträchtigen die Coolify-Oberfläche bis zum Absturz, während ein Build ohne Cache gelingt. Spätere Kommentare nennen weiterhin Next.js-/Coolify-Versionen aus 2026. Ein reproduzierbares Projekt und die Zuordnung zum tatsächlichen Buildprozess fehlen.

### Reproduktion / Prüfszenario

1. Ein kleines Projekt mit festgehaltener Next.js-/Node-Version und identischem Commit wiederholt mit kaltem und warmem Cache bauen.
2. Peak-RSS, cgroup-Speicher, BuildKit-Prozesse, Kernel-OOM-Ereignisse, parallele Builds und Dashboard-Erreichbarkeit messen.
3. Einen aktuellen Dockerfile-/Railpack-Build vergleichen; den historischen Nixpacks-Fall nur zur Ursachenabgrenzung dokumentieren.

### Befunde

- Originalmeldung beschreibt einen Server mit 8 GB RAM ohne Swap und einen gecachten Build mit etwa 3–4 GB Verbrauch; Cacheabschaltung ändere das Verhalten.
- Ein Nutzer verknüpft ähnliche Stillstände mit #6579, weitere Meldungen reichen bis Next.js 16.2.10/Coolify 4.1.2.
- ApplicationDeploymentJob.php setzt limits_memory und CPU-Werte bei der generierten Laufzeit-Compose-Konfiguration. Das ist kein Nachweis entsprechender Grenzen für BuildKit/Next.js während des Builds.
- bootstrap/helpers/applications.php steuert concurrent_builds; unzureichende Reserven oder mehrere Builds können die Systemwirkung verstärken, sind aber noch keine bestätigte Ursache.

### Umsetzungsschritte

- [ ] Die höchste Speicherbelegung einem Prozess und einem Buildschritt zuordnen und Cacheinhalt/-größe reproduzierbar festhalten.
- [ ] Bei Coolify-seitiger Ursache Buildkonkurrenz oder den unterstützten Builder-Ressourcenpfad gezielt korrigieren; Laufzeitlimits nicht als Buildschutz ausgeben.
- [ ] Bei einem reproduzierten Next.js-/Builderproblem ein minimales Upstreambeispiel mit Versionsmatrix erstellen; temporäre Cacheabschaltung als solchen Workaround kennzeichnen.
- [ ] OOM-Abbrüche in Deploymentstatus und Logs sichtbar machen und Queue-/Slotfreigabe mit #6579 absichern.

### Abnahmekriterien und Regressionstests

- [ ] Warmer und kalter Build desselben Testprojekts haben dokumentierte, vergleichbare Speichermessungen.
- [ ] Ein begrenzt scheiternder Build hält die Verwaltungsoberfläche erreichbar und hinterlässt keinen dauerhaft laufenden Queueeintrag.
- [ ] Der gewählte Schutz begrenzt tatsächlich die Buildarbeit und verschlechtert normale Builds nicht unerkannt.

### Offene Fragen und Risiken

- Kein Beispielrepository im Original; die behauptete Cacheabhängigkeit ist noch nicht gegen gleiche Versionen und gleiche Nebenlast kontrolliert.
- Nixpacks ist laut Projektregeln veraltet und wird nicht als neue Zielkonfiguration empfohlen.
- Mehr RAM oder Swap kann Symptome mildern, ersetzt aber keine Ursachenfeststellung.

### Error Message and Logs

When deploying a Next.js app on Coolify, a normal rebuild (with cache) consumes excessive CPU and memory, eventually crashing the server.

Rebuild (with cache): RAM usage spikes to 3–4 GB, CPU load average jumps above 70, and the entire Coolify instance becomes unresponsive (Gateway Timeout).


However, when I use Force Deploy (without cache), the build completes successfully without killing the server.


## Actual Behavior

1. Node.js build process consumes ~3.6 GB RAM (with --max-old-space-size unset).
2. Load average spikes beyond 70.
3. Coolify dashboard becomes unreachable (Gateway Timeout).
5. After killing the Node process, memory usage returns to normal.


## Expected behavior
A rebuild with cache should not consume excessive memory compared to a clean deploy.

## Logs / Metrics

Server: 8 GB RAM, no swap

top shows Node process using ~3.6 GB during rebuild (node --max-old-space-size not set).

Load average spikes > 70, Coolify dashboard becomes unreachable.

After killing the Node process, memory returns to normal.

## Workaround

Using Force Deploy (without cache) avoids the issue but is slower.


### Steps to Reproduce


1. Deploy a Next.js app in Coolify.
2. Choose Rebuild (with cache enabled).
3. Observe memory usage climbing until server becomes unresponsive.
