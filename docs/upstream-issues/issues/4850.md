## Aufarbeitung: 413-Antwort bei großen Uploads der richtigen Schicht zuordnen

**Bereich:** Service / Uploads · **Priorität:** P2 · **Bewertung:** Integration / Dokumentation

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Ein 400-MB-WordPress-Upload schlägt trotz angepasster PHP-Werte fehl. Kommentare nennen vorgeschaltete CDN-/WAF-Limits und Apache als mögliche Quellen. Der Bericht belegt keinen Coolify-eigenen globalen Uploadgrenzwert.

### Reproduktion / Prüfszenario

1. Dieselbe synthetische Datei über Domain, direkt zum eigenen Proxy und über einen geschützten direkten Testzugang hochladen.
2. HTTP-Antwortheader und Logs von CDN/WAF, Proxy, Webserver und PHP vergleichen.
3. Kleine, mittlere und knapp oberhalb des festgestellten Grenzwerts liegende Dateien testen.

### Befunde

- Der Originalbericht verändert nur .htaccess/PHP-Werte.
- Kommentar 2598270524 fragt nach einem vorgeschalteten CDN; eine Bestätigung des Reporters fehlt.
- templates/compose/wordpress-with-mariadb.yaml und bootstrap/helpers/proxy.php trennen Dienst- und Proxy-Konfiguration.

### Umsetzungsschritte

- [ ] Eine Diagnosematrix dokumentieren, die den antwortenden Hop identifiziert.
- [ ] Nur den nachgewiesenen Limitpfad konfigurieren und Zeitlimits sowie Anwendungseinstellungen abstimmen.
- [ ] Falls ein eigenes Template-Limit ursächlich ist, einen verständlichen konfigurierbaren Wert vorsehen.

### Abnahmekriterien und Regressionstests

- [ ] Der Grenzwert und die verantwortliche Schicht sind mit Logs belegt.
- [ ] Ein erlaubter großer Upload funktioniert bis zur Anwendung; zu große Dateien liefern eine verständliche Meldung.
- [ ] Schutzlimits bleiben bewusst gesetzt.

### Offene Fragen und Risiken

- Externe CDN-/WAF-Limits können nicht durch PHP-Konfiguration aufgehoben werden.
- Im Bericht fehlen Proxytyp, vorgeschaltete Anbieter und vollständige Responseheader.

Faced this issue many times.

To add to the above, if you are behind a WAF, check that it's not causing this as well.

If you are running WordPress inside an apache container, you can also increase the upload limit on the apache side by adding this line to your .htaccess:

```
SecRequestBodyLimit 2000000000
```

That's 2GB in bytes as an example
