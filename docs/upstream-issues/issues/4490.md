# Upstream #4490: Berechtigungen erzeugter Bind-Dateien bei Compose-Änderungen erhalten

## Aufarbeitung: Berechtigungen erzeugter Bind-Dateien bei Compose-Änderungen erhalten

**Bereich:** Dateispeicher / Berechtigungen · **Priorität:** P1 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Per content erzeugte Konfigurationsdateien werden nach Compose-Änderung oder Neustart für nicht privilegierte Container unlesbar. Die Diskussion betrifft LibreChat, Supabase/Kong und rootless Docker; Eigentümer, Modus und SELinux sind getrennt zu erfassen.

### Reproduktion / Prüfszenario

1. Dienst mit nicht-root UID/GID und einem content-Bind-Mount bereitstellen.
2. Dateiinhalt, Eigentümer und Modus nach Erststart, Compose-Speichern, Neustart und Hostneustart vergleichen.
3. Mit root- und nicht-root-SSH-Nutzer sowie einem SELinux-Testhost wiederholen.

### Befunde

- Kommentar 3584516155 nennt eine Datei mit Modus 640 und abweichender Kong-UID.
- LocalFileVolume::saveStorageOnServer unterstützt heute chmod/chown und führt standardmäßig chmod +x aus.
- EnsureContentFilesOnServer schreibt fehlende Content-Dateien vor Containerstart; Erstellen und Aktualisieren sind somit verschiedene Pfade.

### Umsetzungsschritte

- [ ] Alle Schreibpfade auf ein konsistentes Verfahren für Eigentümer und Leserechte bringen.
- [ ] Bestehende explizite chmod/chown-Einstellungen bei erneutem Parsen erhalten.
- [ ] Neue sichere Defaults nach Dateityp wählen, ohne Geheimnisse allgemein lesbar zu machen.

### Abnahmekriterien und Regressionstests

- [ ] Nicht-root-Container lesen ihre Konfiguration nach jedem genannten Lebenszyklusschritt.
- [ ] Explizite restriktive Dateirechte bleiben erhalten.
- [ ] Vorhandene Hostdateien werden beim Compose-Update nicht unbegründet umchmodiert.

### Offene Fragen und Risiken

- Globale chmod-777- oder periodische chown-Workarounds sind ungeeignet.
- SELinux-Kontexte sind im Rocky-Bericht nicht dokumentiert.

````markdown
Ran into the same issue with supabase, which also uses the volume bind to create a file with the special coolify `content` parameter:

https://github.com/coollabsio/coolify/blob/v4.x/templates/compose/supabase.yaml#L32-L39

```yml
    volumes:
      # https://github.com/supabase/supabase/issues/12661
      - type: bind
        source: ./volumes/api/kong.yml
        target: /home/kong/temp.yml

          _format_version: '2.1'
          _transform: true

It might be useful to allow setting the UID:GID (chown) and permissions (chmod) for the bind mount.

---

My current workaround is to set the file permissions with a sidecar container:

```yaml
services:
  fix-supabase-kong-file-permission:
    image: alpine:latest
    # We need to fix the permission for the kong config file as coolify seems to
    # set it to 640 for coolify user, but kong operates as user 100.
    # See https://github.com/coollabsio/coolify/issues/4490#issuecomment-3584516155
    command: ash -c 'while true; do sleep 30; chown 100 /mnt/volumes/api/kong.yml ; ls -la /mnt/volumes/api/; done'
    volumes:
      - type: bind
        source: ./volumes/api/
        target: /mnt/volumes/api/
```
````
