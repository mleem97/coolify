## Aufarbeitung: Neustart darf vorhandene Dockerfile-Images nicht unnötig neu bauen

**Bereich:** Deployment und Neustart · **Priorität:** P2 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Der Restart-Knopf startet laut Meldung einen vollständigen Dockerfile-Build. Aktuell wird für Dockerfile-, Docker-Image- und Compose-Buildpacks tatsächlich ein normaler Deployment-Ablauf gewählt; dieser kann einen vorhandenen unveränderten Image-Build aber überspringen.

### Reproduktion / Prüfszenario

1. Dockerfile-Anwendung mit messbar langem Build erfolgreich deployen.
2. Ohne Git- oder Konfigurationsänderung Restart auslösen und Build-Schritte, Image-ID und Laufzeit vergleichen.

### Befunde

- Kommentar bestätigt das Verhalten für ein Python-Image aus GitHub und verweist auf #4018.
- app/Livewire/Project/Application/Heading.php setzt restart_only=true; ApplicationDeploymentJob deaktiviert den Sonderpfad für dockerfile, dockerimage und dockercompose.
- should_skip_build() prüft vorhandenes Commit-Image und Konfigurationsunterschiede; Remote-Build-Secrets oder fehlender Snapshot können einen Build auslösen.

### Umsetzungsschritte

- [ ] Restart-Semantik fachlich festlegen: identisches laufendes Image neu starten oder geänderte Laufzeitkonfiguration neu anwenden.
- [ ] Die Ursache eines Builds im Restart-Ablauf sichtbar machen und fehlenden Cache, Konfigurationsänderung und Secret-Neuauflösung unterscheiden.
- [ ] Gezielt vorhandene Image-Wiederverwendung korrigieren; keinen pauschalen Build-Bypass einführen, der notwendige Änderungen ignoriert.

### Abnahmekriterien und Regressionstests

- [ ] Unverändertes Dockerfile-Deployment startet ohne Docker-Build neu.
- [ ] Bei fehlendem Image und tatsächlicher Build-Konfigurationsänderung erfolgt ein nachvollziehbarer kontrollierter Fallback.
- [ ] Compose-, Docker-Image-, Preview- und zusätzlicher Server behalten die richtige Zielinstanz und Image-Version.

### Offene Fragen und Risiken

- Ein neuer Eintrag in der Deployment-Historie beweist allein noch keinen Neubau.
- Ursprünglich genutzter Cache und Zustand des Image-Registers sind nicht vollständig dokumentiert.
