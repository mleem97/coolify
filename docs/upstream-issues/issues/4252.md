## Aufarbeitung: Private Git-Submodule mit GitHub-App-Zugangsdaten klonen

**Bereich:** Git-Quellen · **Priorität:** P2 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Der Haupt-Clone gelingt, private Submodule schlagen bei der Authentifizierung fehl. HTTPS-Submodule werden im aktuellen Code bereits mit temporären Git-Konfigurationsoptionen unterstützt; die ursprünglich gemeldeten SSH-URLs und verschachtelten Submodule benötigen eine eigene Prüfung.

### Reproduktion / Prüfszenario

1. GitHub-App nur für Test-Hauptrepo und Test-Subrepo installieren.
2. Submodule einmal per HTTPS, einmal per SSH-URL und einmal verschachtelt hinterlegen.
3. Deployment mit aktivierten Submodulen sowie ein Compose-Lesezugriff auf ein Submodul durchführen.

### Befunde

- Die ursprüngliche Fehlermeldung ist Permission denied (publickey) bei einem SSH-Submodul.
- Application::generateGitImportCommands setzt inzwischen URL-Rewrites per git -c für denselben HTTPS-Host.
- tests/Unit/GitHubAppSubmoduleCredentialsTest.php deckt Weitergabe an Clone, sync und update ab; diese Tests wurden hier nicht ausgeführt.

### Umsetzungsschritte

- [ ] HTTPS-Regression zuerst durch vorhandene Tests und einen privaten Test-Clone prüfen.
- [ ] SSH-/relative Submodule mit dem vorhandenen Credential-Pfad konsistent behandeln und App-Installationsrechte prüfen.
- [ ] Zugangsdaten nur pro Befehl einsetzen und in Logs redigieren.

### Abnahmekriterien und Regressionstests

- [ ] Erlaubte private Submodule lassen sich rekursiv laden; nicht freigegebene Repositories scheitern verständlich.
- [ ] Keine Tokens in .gitmodules, globaler Git-Konfiguration, dauerhaftem Checkout oder Logs.
- [ ] Compose in einem Submodul und Base Directory funktionieren gemeinsam.

### Offene Fragen und Risiken

- Ein Installationstoken kann keine Repositories lesen, die der App nicht freigegeben sind.
- Die in einem Kommentar vorgeschlagene Tokenablage in .gitmodules darf nicht übernommen werden.

````markdown
### Error Message and Logs

When using a private submodule within my repository the deployment fails with

## Current behaviour

2. Main repository clones successfully using HTTPS token authentication (`https://x-access-token:<TOKEN>@github.com/...`)
3. When `GIT_SSH_COMMAND="ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null" git submodule update --init --recursive` runs, it fails to authenticate with the private submodule

```
git@github.com: Permission denied (publickey).
fatal: Could not read from remote repository.
```

I think the issue might is caused because `git submodule update` doesnt have either SSH creds or the access token to properly access the private repo.

Relevant code:
https://github.com/coollabsio/coolify/blob/6987e83912baa9739faa86d43af659ec133c7029/app/Models/Application.php#L936

## Possible solutions:
Configure Git globally to use the token for all HTTPS requests to GitHub:
```bash
git config --global url."https://x-access-token:${TOKEN}@github.com/".insteadOf "https://github.com/"
```
````

````markdown
I've implemented a very bad practice solution to get the deployments to work for now.
1. Add a fine grained access token under https://github.com/settings/tokens?type=beta
2. Add access to the private submodule repositories you need
3. Add read-only permissions for `Content` and `metadata`
4. Copy the token
5. adjust your `.gitmodules` file to use this token when accessing the repository, replace `github_pat_XXX` with the actual token

```
[submodule "packages/my-private-submodule"]
	path = packages/my-private-submodule
	url = https://x-access-token:github_pat_XXXXXXXXXXXXXXXXX@github.com/MyOrg/MyPrivateSubmodule.git
	branch = main
```
````
