# Upstream #6502: Leere Teams trotz sichtbarer systemweiter Git-Quellen löschen können

## Aufarbeitung: Leere Teams trotz sichtbarer systemweiter Git-Quellen löschen können

**Bereich:** Teams / Ressourcenbesitz / Löschen · **Priorität:** P2 · **Bewertung:** Möglicherweise bereits adressiert

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Neu angelegte leere Teams konnten laut Bericht wegen einer systemweiten GitHub-App nicht gelöscht werden. Der heutige Code unterscheidet ausdrücklich zwischen Sichtbarkeit und Besitz, zählt systemweite Quellen nicht als Blocker und verschiebt selbst besessene systemweite Quellen beim Löschen zum Root-Team. Ein späterer Bericht über einen fremden Server ist gesondert zu prüfen.

### Reproduktion / Prüfszenario

1. Eine systemweite GitHub-App im Root-Team anlegen, anschließend ein neues Team ohne eigene Projekte, Server oder Quellen erstellen und als Owner löschen.
2. Den Ablauf mit einer systemweiten Quelle im zu löschenden Team testen; deren weitere Verfügbarkeit prüfen.
3. Den später gemeldeten Fall mit sichtbarem Server namens coolify nachstellen und tatsächliches team_id statt nur Anzeigename vergleichen.

### Befunde

- Die Diskussion vom August 2025 unterscheidet systemweite Nutzbarkeit und Besitzerteam; der Reporter präzisiert, dass auch frisch angelegte Teams betroffen seien.
- Team::deletionBlockers() zählt aktuell nur eigene Projekte, Server und nicht systemweite Quellen. sources() ist dagegen bewusst eine breitere Sichtbarkeitsliste.
- Team::deleteOwnedRecords() überträgt eigene systemweite GitHub-/GitLab-/Gitea-Quellen an team_id=0; DeleteTeam prüft den Owner und Sperren in einer Transaktion.
- tests/Feature/Team/TeamDeletionTest.php enthält ausdrücklich den Fall system-wide git sources do not block team deletion.
- Ein Kommentar zu v4.3.19 berichtet eine vermeintliche Abhängigkeit vom Root-Server; dessen tatsächlicher Eigentümer ist aus der Meldung nicht belegt.

### Umsetzungsschritte

- [ ] Die bestehenden Besitztests um fremde sichtbare Quellen und den gemeldeten Root-Server-Fall ergänzen beziehungsweise gezielt ausführen.
- [ ] In der Sperrliste ausschließlich tatsächlich eigene Ressourcen mit nachvollziehbarem Link anzeigen.
- [ ] Übertragung systemweiter Quellen, Sessionwechsel und Rechteprüfung nach Löschung end-to-end verifizieren.

### Abnahmekriterien und Regressionstests

- [ ] Ein wirklich leeres Team ist löschbar, obwohl es systemweite Quellen benutzen kann.
- [ ] Root-Server und fremde Ressourcen werden weder als eigene Blocker behandelt noch gelöscht.
- [ ] Eigene verbleibende Server/Projekte blockieren das Löschen verständlich; nur ein berechtigter Owner kann die Aktion ausführen.

### Offene Fragen und Risiken

- Die heutige Implementierung adressiert den ursprünglichen Fehler sichtbar, ist hier aber nicht zur Laufzeit getestet worden.
- Der spätere Serverbericht kann eine andere Anzeige- oder Besitzzuordnung betreffen.
