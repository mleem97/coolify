## Aufarbeitung: GitHub-Ratelimits von fehlendem Repositoryzugriff unterscheiden

**Bereich:** GitHub-Integration / API / Fehlermeldungen · **Priorität:** P2 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Ein ausgeschöpftes GitHub-Installation-Ratelimit wird beim Anlegen einer privaten Anwendung als nicht gefundenes oder nicht zugängliches Repository gemeldet. Im aktuellen API-Controller werden HTTP 403 und 404 noch immer gemeinsam auf eine 404-Antwort abgebildet.

### Reproduktion / Prüfszenario

1. GitHub-App-basiertes Anlegen einer Anwendung mit einer kontrollierten GitHub-Antwort 403 und X-RateLimit-Remaining=0 testen.
2. Denselben Ablauf mit echter 404, fehlender Berechtigung bei verbleibendem Kontingent, 429 und einer vorübergehenden 5xx-Antwort vergleichen.
3. UI-Import und öffentliche Coolify-API getrennt prüfen, da sie unterschiedliche HTTP-Helfer nutzen.

### Befunde

- Originalbericht zu beta.420.6 benennt das ausgeschöpfte GitHub-App-Limit als tatsächlichen Grund hinter der Repository-not-found-Meldung.
- ApplicationsController::githubAppRepository() gibt aktuell für status()===404 oder 403 dieselbe Repository-not-found-Antwort mit HTTP 404 aus.
- bootstrap/helpers/github.php liefert in githubApi() bereits Rate-Limit-Metadaten und Fehlermeldungen mit Reset-Zeit; der direkte API-Controller-Aufruf nutzt diese differenzierte Fehlerbehandlung nicht.
- GithubPrivateRepository::loadBranchByPage() verarbeitet GitHub-Fehler separat; beide Importpfade benötigen konsistente Semantik.

### Umsetzungsschritte

- [ ] Eine gemeinsame Fehlerklassifizierung für Berechtigung, nicht gefunden, primäres/sekundäres Ratelimit und vorübergehenden Upstreamfehler einführen.
- [ ] Bei Ratelimit die verfügbare Reset-/Retry-After-Information und einen verständlichen nächsten Schritt ausgeben; keine automatische Tokenneuanlage verlangen.
- [ ] HTTP-Tests für die getrennten Fälle ergänzen und sicherstellen, dass weder Installationstoken noch komplette Requestheader in Fehlermeldungen gelangen.

### Abnahmekriterien und Regressionstests

- [ ] 403 mit erschöpftem Kontingent wird als Ratelimit erkannt und enthält keine falsche Aussage über die Existenz des Repositorys.
- [ ] Ein echtes Zugriffsproblem bleibt von Ratelimit und GitHub-Ausfall unterscheidbar.
- [ ] UI und API liefern hilfreiche, konsistente Fehler; Retry bleibt begrenzt und respektiert die Upstreamvorgaben.

### Offene Fragen und Risiken

- 403 kann mehrere Gründe haben; Header, Antworttext und Status müssen gemeinsam ausgewertet werden.
- Die Codeprüfung bestätigt die falsche Zusammenfassung, ohne das GitHub-Kontingent real zu erschöpfen.

### Error Message and Logs

# GitHub API Rate Limit Error Handling

## Problem
When creating a new application using a private GitHub repository, users encounter the following error:

```
{
    "message": "Repository not found."
}
```

This error is misleading and does not reflect the actual issue, causing confusion for users.

## Root Cause
The underlying issue is that the GitHub API rate limit has been exceeded for the GitHub App installation. The error response from the API is:

```yaml
GitHub API call failed:
Error: API rate limit exceeded for installation ID 78061994.
Rate Limit Status:
- Remaining Calls: 0
- Reset Time: 2025-07-30 21:12:38 UTC
```

This rate limit exhaustion prevents the system from accessing the repository, but the error message incorrectly suggests a permissions or repository access issue.

## Impact
The vague error message leads to user confusion, as it implies a problem with repository permissions or existence rather than a temporary API rate limit issue. This can result in unnecessary troubleshooting and delays in resolving the actual problem.

## Expected Behavior
The system should display a clear and actionable error message that:
- Indicates the GitHub API rate limit has been exceeded.
- Provides the reset time for the rate limit (derived from the `x-ratelimit-reset` header).
- Includes a link to relevant GitHub documentation for further assistance.
- Optionally, provides the GitHub request ID for support follow-up.

Example of a user-friendly error message:
```
GitHub API rate limit exceeded. Please try again after 2025-07-30 21:12:38 UTC. For more details, visit https://docs.github.com/en/rest/overview/rate-limits-for-the-rest-api. Request ID: ABC123.
```

## Suggested Fix
To address this issue, implement improved error handling in the application by:

1. **Parsing the GitHub API Error Response**:
   - Check for rate limit errors by inspecting the HTTP status code (403) and the error message for phrases like "API rate limit exceeded."
   - Extract the `x-ratelimit-reset` header to determine when the rate limit will reset.
   - Optionally, capture the `x-github-request-id` header for support purposes.

2. **Displaying a User-Friendly Message**:
   - Construct a clear message that explains the rate limit issue.
   - Convert the `x-ratelimit-reset` timestamp (Unix epoch) to a human-readable UTC date and time.
   - Include a link to GitHub's rate limit documentation: https://docs.github.com/en/rest/overview/rate-limits-for-the-rest-api.
   - If available, include the GitHub request ID for traceability.

3. **Implementation Steps**:
   - Update the API client to handle rate limit errors specifically.
   - Format the error message using a template that incorporates the reset time and documentation link.
   - Log the full error details (including request ID) for debugging and support purposes, but display only the user-friendly message to the end user.

4. **Example Pseudocode**:
```python
def handle_github_api_error(response):
    if response.status_code == 403 and "API rate limit exceeded" in response.text:
        reset_time = datetime.utcfromtimestamp(int(response.headers.get('x-ratelimit-reset', 0)))
        request_id = response.headers.get('x-github-request-id', 'N/A')
        error_message = (
            f"GitHub API rate limit exceeded. Please try again after {reset_time} UTC. "
            f"For more details, visit https://docs.github.com/en/rest/overview/rate-limits-for-the-rest-api. "
            f"Request ID: {request_id}."
        )
        return error_message
    return "An unexpected error occurred. Please try again later."
```

## Additional Considerations
- **Proactive Rate Limit Monitoring**: Monitor the `x-ratelimit-remaining` header to warn users or throttle requests before the limit is reached.
- **Retry Mechanism**: Implement an automatic retry after the reset time for non-critical operations, with appropriate user notification.
- **User Guidance**: Provide in-app suggestions for users to check their GitHub App installation settings or contact GitHub support if the issue persists.

By implementing these changes, the application will provide clearer feedback to users, reduce confusion, and improve the overall user experience when encountering GitHub API rate limit issues.
