## Aufarbeitung: Compose-Previews mit mehreren Dateien und stabilen Servicenamen ermöglichen

**Bereich:** Compose-Previews · **Priorität:** P1 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Coolify benennt Preview-Services um, bearbeitet aber nur die ausgewählte Compose-Datei. Bei Merge-Dateien stehen dann leere Services unter neuem Namen neben den ursprünglichen Definitionen; außerdem brechen Verweise aus Konfigurationsdateien und teils Bind-Pfade.

### Reproduktion / Prüfszenario

1. Drei Compose-Dateien mit Basisservices und einer Override-Datei ohne eigene Images zusammenführen.
2. Produktion und zwei Preview-PRs deployen; interne DNS-Namen, depends_on, Konfigurations-Bind-Mounts und benutzerdefinierte Serviceziele prüfen.

### Befunde

- Originalfehler: tempo-pr-64 besitzt nach Bearbeitung weder Image noch Build-Kontext.
- Kommentar vom 29.08.2026 ergänzt Fehler bei Bind-Dateinamen, Monitoring-Services und Custom-Start-Befehlen.
- bootstrap/helpers/parsers.php suffixiert weiterhin Servicenamen; es existieren mittlerweile Netzwerk-Aliasse für ursprüngliche Hostnamen, die das vollständige Mehrdatei-Mergeproblem nicht lösen.

### Umsetzungsschritte

- [ ] Mit #5921 eine einzige vollständige Compose-Auflösung vor Coolify-Anpassungen definieren.
- [ ] Service-Schlüssel möglichst stabil halten und Isolation über Projekt-, Container-, Netzwerk- und Volume-Namen gewährleisten; vorhandene Preview-Migration beachten.
- [ ] Externe Konfigurationsdateien und relative Bind-Quellen unverändert lassen, sofern kein tatsächliches Preview-Datenvolume gemeint ist.

### Abnahmekriterien und Regressionstests

- [ ] Mehrdatei-Projekt besitzt nach Auflösung für jeden Service ein korrektes Image oder Build-Ziel.
- [ ] Interne Hostnamen und depends_on bleiben gültig; Custom-Start mit Originalservicenamen funktioniert.
- [ ] Zwei Previews teilen keine schreibbaren Volumes mit Produktion oder miteinander, außer bei ausdrücklich externen Ressourcen.

### Offene Fragen und Risiken

- Das Entfernen aller Suffixe ohne Prüfung von Volumes und Legacy-Netzwerken wäre unvollständig.
- Neue Alias-Behandlung kann einen Teil der historischen Symptome bereits abfangen.

### Additional Information

#### My current setup

My application builds with the following command

```sh
docker compose -f docker/dependencies.docker-compose.yml -f docker/metrics.docker-compose.yml -f docker/prod.docker-compose.yml build
```

I set the `Docker Compose Location` to `prod.docker-compose.yaml`.

This is my `prod.docker-compose.yml`:

```yml
name: ripste-prod

services:
  api:
    build:
      context: .
      dockerfile: dockerfile
      target: api
    environment:
      - POSTGRES_HOST=postgres
      - REDIS_HOST=redis
      - OTLP_URL=http://tempo:4317
    env_file:
      - path: .env
        required: false

  # Reference services from dependencies and metrics
  # Making services available in all other services
  # Making services available to reference in Coolify
  grafana:
  prometheus:
  tempo:
  loki:
  postgres:
  redis:
```

Real definition of the services (except api) is in `dependencies.docker-compose.yml` and `metrics.docker-compose.yml` where the images are specified.

#### Normal behavior

So what Coolify does (I think) in a "normal" deployment:

 - treat the services available in my prod config by adding some Coolify specific configuration
 - replace the `prod.docker-compose.yml` by the newly generated file

#### Cause of the bad behavior

In preview deployments, in addition to the original edits, the service names (keys under the `services` entry) are also renamed to `{container_name}-pr-{id_pr}` (it's also the new `container_name`).

However, as the images for Postgres or all services are set in `dependencies.docker-compose.yml` and `metrics.docker-compose.yml`, and that those files are not modified because they are not specified in `Docker Compose Location`, the service names do not match anymore, and the newly generated `prod.docker-compose.yml` does not have the image information (that came from the other compose files).

I think the issue is here:

https://github.com/coollabsio/coolify/blob/abde78094a2b50df769691b944fe040817736162/app/Jobs/ApplicationDeploymentJob.php#L1766

I know that Coolify does not officially support multi files Docker Compose, however I think this issue with multi files Docker Compose and Preview Deployments could be fixed by remove the renaming of the services.

I think this will not have an impact on other features like rolling updates, because we would still keep the `container_name` value edit and will just change/"let as it is" the service name with which Docker Compose reference between them.

```markdown
+1 on removing the service renaming — I hit the same wall from a different angle, without multi-file compose.

Single `docker-compose.yml`, one app service plus a monitoring stack (Prometheus, Grafana, Loki, Promtail, node-exporter). Production deploys fine. On preview deployments Coolify rewrites the compose and suffixes the **service names** with `-pr-{id}`, which breaks two things:

1. Bind-mounted config files. The generated compose ends up looking for `prometheus.yml-pr-9`, `loki-config.yaml-pr-9`, etc. Those files obviously don't exist in the repo, so the deployment fails.
2. Any reference between services (`depends_on`, hostnames in config files) still points at the original names.

Workarounds I tried, none of which hold:

- **Preserve Repository During Deployment** — not respected on previews (#5084).
- **Compose profiles** to keep monitoring out of previews — ignored entirely; Coolify creates `prometheus-<uuid>-pr-11`, `grafana-<uuid>-pr-11`, etc. anyway.
- **Custom start command** `docker compose up -d app` — fails with `no such service: app`, since the service is now `app-pr-11`. And whatever name you hardcode is wrong in the other environment.
- **Post-deployment script** stopping the monitoring containers by matching the `-pr-` suffix — works, but it's a hack, and everything still gets built and started first.

The end result is that preview deployments are effectively unusable for any compose file with more than one service, which is a shame because that's exactly where they'd be most valuable.

Agreed with the proposal in the original report: keep suffixing `container_name` so containers stay unique per PR, but leave the compose **service** names untouched. Compose already isolates preview stacks via the project name, so the service-level rename doesn't seem to buy anything, and it's what breaks mounts and cross-service references.

Happy to test a branch if it helps.
```
