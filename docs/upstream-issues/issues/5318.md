# Upstream #5318: force-Deployment für Services an den Image-Pull weitergeben

## Aufarbeitung: force-Deployment für Services an den Image-Pull weitergeben

**Bereich:** API / Deployment · **Priorität:** P1 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Ein API-Deploy mit force=true zieht bei Services kein aktuelles Image, während der entsprechende UI-Befehl dies tut. Der aktuelle Service-Zweig ignoriert den bereits eingelesenen force-Wert und ruft StartService ohne pullLatestImages auf.

### Reproduktion / Prüfszenario

1. Testregistry-Tag auf Image A setzen und einen Compose-Service daraus starten.
2. Unter demselben Tag Image B veröffentlichen und /api/v1/deploy?uuid=...&force=true aufrufen.
3. Image-Digest mit einem anschließenden UI-Aufruf Pull latest images and restart vergleichen.

### Befunde

- Der ursprüngliche Endpoint ist veraltet; Kommentare bestätigen den Fall auch über /api/v1/deploy.
- Kommentar 3982135825 identifiziert den Service-Zweig.
- DeployController::deploy_resource ruft im aktuellen Service::class-Zweig StartService::run($resource) auf, obwohl force als Parameter vorliegt.

### Umsetzungsschritte

- [ ] Semantik von force für Services festlegen und ausdrücklich an StartService beziehungsweise den aktuellen Queuepfad weitergeben.
- [ ] API und UI auf dieselbe Image-Pull-Option führen.
- [ ] force=false und explizite Compose-pull_policy getrennt erhalten.

### Abnahmekriterien und Regressionstests

- [ ] force=true startet nachweislich Image B und meldet einen fehlgeschlagenen Pull als Fehler.
- [ ] force=false folgt der dokumentierten Standard-/pull_policy-Semantik.
- [ ] Berechtigungsprüfung und Verhalten von Application-Ressourcen bleiben erhalten.

### Offene Fragen und Risiken

- Immer ungefragt pullLatestImages=true zu setzen würde force=false ebenfalls verändern.
- Ein unveränderlicher Digest muss weiterhin exakt dieses Image referenzieren.

````markdown
## Root Cause Found

The bug is in `app/Http/Controllers/Api/DeployController.php` (line ~502).

When deploying a **Service** via the API/webhook, `StartService::run()` is called **without** `pullLatestImages: true`:

```php
// DeployController.php — current code
case Service::class:
    StartService::run($resource);  // ← pullLatestImages defaults to false
    break;
```

While `StartService::handle()` signature is:

```php
public function handle(Service $service, bool $pullLatestImages = false, bool $stopBeforeStart = false)
```

Since `pullLatestImages` defaults to `false`, `docker compose pull` is **never executed** when deploying via API/webhook. The deployment just runs `docker compose up -d --force-recreate`, which reuses the locally cached image.

In contrast, the **UI** (`Livewire/Project/Service/Heading.php`) correctly passes the parameter:

```php
// Heading.php — UI deploy buttons all pass pullLatestImages: true
StartService::run($this->service, pullLatestImages: true);
```

## One-Line Fix

```php
// DeployController.php — fix
case Service::class:
    StartService::run($resource, pullLatestImages: true);
    break;
```

## Reproduction & Verification

Our CI/CD pipeline (GitHub Actions → ghcr.io → Coolify webhook) consistently deployed stale images. After applying this one-line patch inside the Coolify container, auto-deploy immediately started pulling the latest image correctly.
````

</details>
