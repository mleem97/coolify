## Aufarbeitung: HTTP/2-Protokollfehler am Cloud-Deploy-Endpunkt eingrenzen

**Bereich:** Coolify Cloud / API-Transport / GitHub Actions · **Priorität:** P2 · **Bewertung:** Integration / Dokumentation

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Ein curl-Aufruf aus GitHub Actions zum Coolify-Cloud-Deploy-Endpunkt bricht mit HTTP/2 PROTOCOL_ERROR ab; mit HTTP/1.1 funktioniert er laut Bericht. Das weist auf einen Transport-/Proxyfall hin, belegt aber keinen Fehler im lokalen Deploy-Controller des Forks.

### Reproduktion / Prüfszenario

1. Mit einem ungefährlichen Testdeployment denselben authentisierten API-Aufruf über HTTP/2 und HTTP/1.1 durchführen und Request-ID, Status sowie bereinigte Header erfassen.
2. Vor jedem erneuten Auslösen prüfen, ob der erste Request bereits ein Deployment erzeugt hat.
3. Den Cloud-Endpunkt mit einer selbst gehosteten Instanz vergleichen; curl-Version, Runner-Image und Proxyversion festhalten.

### Befunde

- Originalmeldung zu beta.428 auf Coolify Cloud zeigt curl-Fehler 92; der Reporter nennt --http1.1 als funktionierenden Workaround.
- app/Http/Controllers/Api/DeployController.php verarbeitet Deploymentanforderungen auf Anwendungsebene; TLS-/HTTP/2-Verhandlung liegt vor diesem Controller.
- Die gemeldete Domain app.coolify.io und deren vorgelagerte Cloud-Infrastruktur gehören nicht automatisch zum untersuchten Fork.

### Umsetzungsschritte

- [ ] Den Transportfehler mit einem minimalen, geheimnisfreien Request-/Responsebeleg an der betroffenen Cloud-Proxykonfiguration eingrenzen.
- [ ] HTTP/1.1 als begrenzten, dokumentierten Workaround behandeln, sofern der Nutzer diesen Endpunkt betrifft; keine globale Protokolländerung im Produkt ohne Reproduktion.
- [ ] Bei abgebrochener Antwort den Deploymentzustand abgleichen, bevor ein Client denselben nicht sicher idempotenten Start erneut sendet.

### Abnahmekriterien und Regressionstests

- [ ] Der betroffene Cloud-Endpunkt liefert für den dokumentierten HTTP/2-Test eine vollständige Antwort oder eine nachvollziehbare HTTP-Fehlermeldung.
- [ ] Ein Transportretry erzeugt nicht unbemerkt mehrere Deployments.
- [ ] Selbst gehostete Deployments und vorhandene API-Clients behalten ihre bisherige Funktion.

### Offene Fragen und Risiken

- Cloud-Edge-Konfiguration und Serverlogs sind nicht zugänglich; ein reiner Fork-Codepatch kann den Fehler möglicherweise nicht lösen.
- Der ursprüngliche Request kann trotz fehlgeschlagener curl-Antwort serverseitig bereits verarbeitet worden sein.

### Error Message and Logs

Hello,

I use a github action to run a `curl` command on the `https://app.coolify.io/api/v1/deploy` endpoint.
But keep getting this error from curl: `curl: (92) HTTP/2 stream 0 was not closed cleanly: PROTOCOL_ERROR (err 1)`
My Github action steps:
```
    steps:
      - name: Trigger Coolify Deployment
        run: |
          curl --fail-with-body 'https://app.coolify.io/api/v1/deploy?uuid=${{ env.COOLIFY_RESOURCE }}&force=true' \
          --header 'Authorization: Bearer ${{ secrets.COOLIFY_TOKEN }}' \
          --header 'Content-Type: application/json'
```
By adding `--http1.1` to the curl command, the issue is resolved so i concluded there's an issue with HTTP2 protocol on the coolify end.
