## Aufarbeitung: Wildcard-Routing abhängig von der tatsächlich laufenden Traefik-Version prüfen

**Bereich:** Proxy / Traefik / Wildcard-Domains · **Priorität:** P1 · **Bewertung:** Möglicherweise bereits adressiert

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Der Bericht belegt eine für Traefik 3.6.13 problematische Host-Wildcardregel und daraus folgende 503-Antworten. Die zentrale Rahmenbedingung hat sich geändert: Seit Traefik 3.7.0 unterstützt Host selbst Wildcard-Subdomains, und der aktuelle Coolify-Generator verwendet standardmäßig traefik:v3.7. Ein pauschaler Ersatz durch HostRegexp wäre deshalb kein sachgerechter heutiger Fix.

### Reproduktion / Prüfszenario

1. Die im Issue gezeigte Wildcard-FQDN mit kontrolliertem Testzertifikat einmal unter Traefik 3.6.13 und einmal unter der aktuellen 3.7-Standardkonfiguration testen.
2. Die tatsächlich laufende Image-Version, v3-Regelsyntax, erzeugte Labels und Routerregistrierung erfassen; ein Coolify-Upgrade allein beweist kein Proxyupgrade.
3. Direkte Subdomain, Domainwurzel, tiefere Subdomain und eine fremde ähnlich geschriebene Domain gegen HTTP und HTTPS testen.

### Befunde

- Das Issue enthält konkrete Host(`*.example.com`)-Labels und eine HostSNI-Fehlermeldung unter Traefik 3.6.13.
- fqdnLabelsForTraefik() in bootstrap/helpers/docker.php erzeugt weiterhin Host-Regeln; bootstrap/helpers/proxy.php verwendet für neue Standardkonfigurationen inzwischen traefik:v3.7.
- Die am 10.11.2026 geprüfte offizielle Traefik-Migrationsdokumentation nennt Wildcard-Unterstützung in Host und HostSNI seit v3.7.0, nur mit v3-Regelsyntax.
- Die aktuelle Dokumentation bevorzugt bei unterstützter Version den Wildcard-Hostmatcher gegenüber HostRegexp, unter anderem wegen TLS-Optionszuordnung.

### Umsetzungsschritte

- [ ] Zuerst den aktuellen Standard mit realem Routingtest bestätigen und vorhandene Installationen mit älteren oder eigenen Proxykonfigurationen identifizieren.
- [ ] Für nicht unterstützte Proxyversionen eine klare Kompatibilitätsmeldung oder einen gezielt versionierten Fallback planen; keinen unnötigen globalen Regexwechsel durchführen.
- [ ] Bei einem erforderlichen HostRegexp-Fallback Hostname korrekt escapen, Matchgrenzen definieren und Zertifikatsdomain-/TLS-Optionsverhalten gesondert absichern.
- [ ] Die vorhandene Proxyversionserkennung nutzen, damit gespeicherte alte Konfigurationen nicht still als kompatibel gelten.

### Abnahmekriterien und Regressionstests

- [ ] Unter der unterstützten Standardversion routet eine direkte Wildcard-Subdomain ohne Routerfehler und ohne 503 durch die Regelkonstruktion.
- [ ] Wildcard und Domainwurzel bleiben entsprechend ihrer definierten Semantik getrennt; fremde Domains werden nicht versehentlich erfasst.
- [ ] Alte Proxyversionen erhalten einen nachvollziehbaren Upgrade-/Kompatibilitätspfad.
- [ ] HTTPS-Zertifikat, explizite Domains und zusätzliche Server funktionieren auch nach der gewählten Änderung.

### Offene Fragen und Risiken

- Die aktuelle Standardkonfiguration spricht für eine Lösung des historischen Falls, ersetzt aber keinen Laufzeittest.
- Eigene oder gespeicherte Proxykonfigurationen können weiterhin Traefik 3.6 verwenden.
- DNS-01-Zertifikatsbeschaffung und Routing sind getrennte Teilprobleme; der Bericht sagt ausdrücklich, dass die Zertifikatserstellung bereits gelang.

### Error Message and Logs

When an application's FQDN field is set to a wildcard (e.g. `*.example.com`), Coolify generates a Traefik router rule using `Host()`. Traefik 3.x rejects this because wildcards are invalid in `Host()` matchers (a single-host rule compiles down to a `HostSNI` matcher for the TLS router, and `HostSNI` does not accept wildcards either). The router never registers, so every request to any wildcard subdomain returns HTTP 503 "Service Unavailable".

Traefik error (from `coolify-proxy` container logs):

```
error while adding rule HostSNI(`*.example.com`): invalid value for HostSNI matcher, "*.example.com" is not a valid hostname
```

Generated Traefik labels on the affected app's container (filtered to `traefik.*` only, via `docker inspect <container> | jq '.[0].Config.Labels | with_entries(select(.key | startswith("traefik.")))'`):

```
traefik.http.routers.http-1-<router-id>.rule=Host(`*.example.com`) && PathPrefix(`/`)
traefik.http.routers.http-1-<router-id>.entryPoints=http
traefik.http.routers.http-1-<router-id>.middlewares=redirect-to-https
traefik.http.routers.http-1-<router-id>.service=http-1-<router-id>
traefik.http.routers.https-1-<router-id>.rule=Host(`*.example.com`) && PathPrefix(`/`)
traefik.http.routers.https-1-<router-id>.entryPoints=https
traefik.http.routers.https-1-<router-id>.tls=true
traefik.http.routers.https-1-<router-id>.tls.certresolver=letsencrypt
traefik.http.routers.https-1-<router-id>.service=https-1-<router-id>
traefik.http.services.https-1-<router-id>.loadbalancer.server.port=3000
```

Observed HTTP behavior:

```
$ curl -iskL https://anything.example.com
HTTP/2 503
```

The exact-FQDN router for the same app (e.g. `example.com`) works correctly; only the wildcard FQDN router fails. TLS wildcard cert provisioning via DNS-01 (Cloudflare provider) succeeded — this is purely a routing-rule construction issue.

### Steps to Reproduce

1. On Coolify v4.0.0-beta.472, create any application (any build pack — reproduced with a Nixpacks Next.js app on port 3000, but the bug is in label generation and is build-pack-independent).
2. In the application's Configuration, set the **Domains** field to include a wildcard entry, e.g. `https://*.example.com` (alongside or instead of an explicit FQDN).
3. Add a wildcard DNS A/AAAA record `*.example.com` → Coolify host IP so arbitrary subdomains resolve.
4. Deploy the application. Coolify provisions a wildcard TLS cert (via DNS-01 if configured) successfully, but Traefik fails to register the wildcard router.
5. `curl -iskL https://anything.example.com` → HTTP 503.
6. `docker logs coolify-proxy 2>&1 | grep HostSNI` shows the error quoted above.
7. `docker inspect <app-container> | jq '.[0].Config.Labels'` shows the `Host(\`*.x\`)` rule quoted above.

### Additional Information

**Root cause hypothesis**
The label generator in `bootstrap/helpers/docker.php` (function `fqdnLabelsForTraefik()`, around lines 598-603) unconditionally emits ``Host(`{$host}`) && PathPrefix(`{$path}`)`` for every FQDN entry, regardless of whether `$host` contains a wildcard. Traefik 3.x rejects wildcards in `Host()` because the matcher compiles to `HostSNI` for TLS, which only accepts literal hostnames.

**Suggested fix**
When `$host` contains `*`, emit a `HostRegexp()` rule instead of `Host()`. For `*.example.com`, the equivalent anchored regex would be:

```
HostRegexp(`^[a-z0-9-]+\.example\.com$`)
```

Key points for the fix:
- Anchor with `^…$` so the regex matches only the intended level (not accidentally deeper nestings or unrelated hostnames)
- Escape dots in the base domain (`\.`)
- Restrict the subdomain character class appropriately (`[a-z0-9-]+` matches the DNS label charset; `[a-zA-Z0-9_-]+` if you want to be looser)
- Apply the same conversion to both the plain-HTTP and the TLS router rule

**Prior art**
- #7859 (closed) reported the same pattern against v4.0.0-beta.460. The community comments there also identify `HostRegexp` as the correct replacement but no fix PR was linked before it closed. This report adds the concrete generated-label output and the exact Traefik error which #7859 lacked.
- #5422 (open) covers wildcard domain issues in a multi-server context and is related but broader.

Happy to retest against any fix, or to expand the reproduction case if additional evidence would help triage.

**Version footnote**
Not yet tested on v4.0.0-beta.473 (one release newer); release notes don't mention wildcard / FQDN / Traefik rule generation changes. Happy to retest if maintainers confirm a fix landed in a newer beta.
