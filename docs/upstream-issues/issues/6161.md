## Aufarbeitung: Abschlusszeit bei Deployment-Timeouts zuverlässig speichern

**Bereich:** Deployment / Status / Zeitmessung · **Priorität:** P2 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Ein durch das Worker-Timeout beendetes Deployment kann als fehlgeschlagen angezeigt werden, während finished_at leer bleibt und die Oberfläche ständig eine gerade erst erfolgte Beendigung suggeriert. Der aktuelle Code schreibt den Zeitstempel im finally-Block des normalen Jobs, nicht im separaten failed()-Pfad.

### Reproduktion / Prüfszenario

1. Ein Testdeployment mit absichtlich länger laufendem Schritt als das konfigurierten Worker-Timeout starten.
2. Das tatsächliche Worker-Timeout auslösen, nicht nur eine reguläre Exception im handle()-Ablauf.
3. Status, finished_at und Anzeige nach mehreren Seitenaktualisierungen prüfen; zusätzlich reguläres Scheitern und Benutzerabbruch vergleichen.

### Befunde

- Die Meldung zu beta.420.5 beschreibt finished_at=NULL nach Timeout und eine wiederholt auf null Sekunden zurückfallende Abschlussanzeige.
- app/Jobs/ApplicationDeploymentJob.php setzt finished_at im finally-Block von handle(). failed(Throwable) ruft failDeployment() auf, aktualisiert jedoch keinen Abschlusszeitstempel.
- updateDeploymentStatus() und ApplicationDeploymentQueue::setStatus() schreiben nur status; bei einem Worker-Abbruch ist das Durchlaufen des handle()-finally nicht verlässlich.
- Ein Kommentar schlägt einen globalen SQL-Update aller NULL-Zeitstempel vor; dieser wäre wegen laufender Deployments und erfundener historischer Zeitpunkte kein geeigneter Fix.

### Umsetzungsschritte

- [ ] Terminale Statuswechsel einschließlich failed() idempotent um finished_at ergänzen; bereits vorhandene Abschlusszeiten erhalten.
- [ ] Für hart abgebrochene Jobs einen kontrollierten Reconciliation-Pfad mit belegtem Abbruchzeitpunkt beziehungsweise ausdrücklich unbekannter Zeit vorsehen.
- [ ] Die Oberfläche soll bei unbekanntem Abschlusszeitpunkt keine scheinbar präzise relative Zeit berechnen.

### Abnahmekriterien und Regressionstests

- [ ] Ein echter Timeout setzt failed und einen stabilen Abschlusszeitpunkt, auch wenn handle()-finally nicht ausgeführt wurde.
- [ ] Mehrfache Failure-Callbacks verändern eine bereits gespeicherte Abschlusszeit nicht.
- [ ] Laufende und wartende Deployments behalten finished_at=NULL; historische unbekannte Zeiten werden nicht pauschal auf jetzt gesetzt.

### Offene Fragen und Risiken

- Ein Codepfaddefizit ist nachgewiesen; ein echter Worker-Timeout wurde in dieser Analyse nicht ausgeführt.
- Ein harter Prozess-/Hostausfall kann auch failed() verhindern und benötigt gesonderte Wiederherstellung.

````markdown
I had an issue where a build hung the server and I had to restart it, after fixing the root cause everything was okay until 1 day later I received a notification for the failed deployment from the previous day. I noticed it also didn't have the finishing time set.

To manually clean up these failed deployments I had to go to the server terminal and execute this:

```
docker exec -it coolify-db psql -U coolify
UPDATE application_deployment_queues SET finished_at = NOW() WHERE finished_at IS NULL;
```

Of course, make sure you have no deployments running at the time of updating this table. Otherwise you'll have to find the correct ID and update only that.
````
