## Aufarbeitung: Externe Pull-Request-Previews vor dem Build gezielt freigeben

**Bereich:** GitHub / Preview-Deployments / Freigaben · **Priorität:** P1 · **Bewertung:** Erweiterung

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Gewünscht ist ein Freigabeablauf für Vorschauen externer Pull Requests. Ein verknüpfter Maintainer-Kommentar beschreibt einen wartenden Zustand und eine Freigabe durch berechtigte Repository-Maintainer, bevorzugt über GitHub-App/OAuth. Der aktuelle Pfad bietet vor allem einen Schalter für öffentliche Fork-Previews; ein entsprechender Freigabezustand fehlt im geprüften Ablauf.

### Reproduktion / Prüfszenario

1. Auf einer Testanwendung mit GitHub-App einen Pull Request aus einem externen Fork öffnen und das Verhalten bei deaktivierten/aktivierten öffentlichen PR-Deployments dokumentieren.
2. Den gewünschten Ablauf als Zustandsfolge festlegen: neuer Commit wartet, berechtigter Maintainer genehmigt genau diesen Commit, danach wird gebaut.
3. Einen weiteren Push, geschlossenes PR, doppelte Freigabe und entzogene Repositoryrechte als separate Fälle durchgehen.

### Befunde

- Das Issue verweist auf #6546; der zusätzlich abgerufene Kommentar issuecomment-3261624121 beschreibt Pending-Previews, einen GitHub-Kommentar/Button und Berechtigungsprüfung per OAuth, alternativ eine Coolify-Freigabe.
- Der Kommentar im Issue verknüpft den Bedarf mit #6536.
- ProcessGithubPullRequestWebhook::handleOpenAction() blockiert externe Forks, wenn is_pr_deployments_public_enabled deaktiviert ist; bei Erlaubnis erzeugt es die Vorschau und reiht das Deployment unmittelbar ein.
- SECURITY.md behandelt Repositoryinhalt als für die jeweilige Ausführung vertrauenswürdig; die neue Freigabe muss diesen Übergang ausdrücklich und prüfbar abbilden.

### Umsetzungsschritte

- [ ] Einen persistenten Freigabezustand mit Repository, PR, Head-SHA, genehmigender Identität und Zeitstempel modellieren.
- [ ] GitHub-OAuth beziehungsweise vorhandene Coolify-Berechtigung serverseitig gegen das richtige Repository und die richtige Ressource prüfen; einen genehmigten SHA vor Queue-Aufnahme erneut vergleichen.
- [ ] Neue Commits verlangen eine neue Freigabe; PR-Schließung und Rechteentzug sperren ausstehende Aktionen. Callback und Webhooks idempotent behandeln.
- [ ] GitHub-Kommentar und Coolify-UI sollen wartend, genehmigt, abgelehnt und veraltet verständlich anzeigen.

### Abnahmekriterien und Regressionstests

- [ ] Externer Code wird vor gültiger Freigabe nicht gebaut oder gestartet.
- [ ] Freigabe gilt nur für den geprüften Head-SHA; ein späterer Push kann sie nicht still übernehmen.
- [ ] Unberechtigte Nutzer und Nutzer anderer Teams können nicht freigeben; doppelte Callback-Zustellung erzeugt höchstens ein Deployment.
- [ ] Bestehende interne Branch-Previews und das Aufräumen geschlossener PRs funktionieren weiter.

### Offene Fragen und Risiken

- Das genaue UX-Produktziel für GitHub-OAuth gegenüber Coolify-Freigabe ist als Architekturentscheidung festzuhalten; der Maintainer bevorzugte GitHub-App, hatte den Ablauf aber nicht getestet.
- Der Befund beschreibt eine fehlende gewünschte Funktion, keinen hier nachgewiesenen unbefugten Zugriff.
- Keine öffentliche Schwachstellenmeldung oder Remote-Aktion wurde ausgeführt.
