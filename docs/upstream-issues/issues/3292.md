## Aufarbeitung: Compose-Vorschauen mit langen YAML-Strukturen ohne Typfehler parsen

**Bereich:** Compose / Preview · **Priorität:** P2 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Preview-Deployments scheitern mit Array to string conversion. Die Diskussion enthält mehrere mögliche Auslöser, darunter gemischte environment-Syntax und gültige lange Compose-Formen. Die pauschale Empfehlung, gültige Arrays zu entfernen, ist keine belastbare Fehlerbehebung.

### Reproduktion / Prüfszenario

1. Eine reduzierte Compose-Anwendung einmal normal und einmal als PR deployen.
2. depends_on mit condition/required, lange ports-/volumes-Form und command-/healthcheck-Arrays jeweils einzeln ergänzen.
3. Mehrere Domains und beide gültigen environment-Formen getrennt testen.

### Befunde

- Der Originalbericht nennt beta.323 bis beta.325; der Autor meldet denselben Fehler auch mit konsistenter environment-Syntax in beta.341.
- Kommentar 2990321785 enthält weitere Hypothesen, aber keine hier verifizierte Stacktrace-Ursache.
- Aktuelle Parser und Preview-Bind-Mount-Tests behandeln bereits strukturierte Compose-Werte.

### Umsetzungsschritte

- [ ] Den kleinsten tatsächlich fehlschlagenden gültigen Compose-Fall als Parser-Fixture sichern.
- [ ] String-Operationen an dieser Stelle durch typgerechte Behandlung von Liste/Mapping ersetzen.
- [ ] Ungültige gemischte environment-Einträge früh mit Pfad und verständlicher Meldung ablehnen.

### Abnahmekriterien und Regressionstests

- [ ] Gültige lange und kurze Compose-Formen erzeugen semantisch gleichwertige Ergebnisse in Produktion und Preview.
- [ ] Kein Array-to-string-Warning; depends_on.condition und Portoptionen bleiben erhalten.
- [ ] Parser-Snapshot-Diff enthält nur beabsichtigte Änderungen.

### Offene Fragen und Risiken

- Ein YAML-Linter allein prüft keine vollständige Compose-Semantik.
- Kein aktueller Stacktrace aus dem Fork liegt vor.

Hi @gabrielalmeida something you could try is declare the `environment` variables in a uniform way.
The syntax that works for me (on multiple docker files across different resources/projects on Coolify) is:

```
environment:
  - 'VAR_NAME=VAR_VALUE'
```

Mixing styles/syntax could cause things to break e.g. the dashboard service above has

```
environment:
      - HASURA_ENDPOINT=http://hasura:8080/v1/graphql
      - S3_ENDPOINT=http://minio:9000
      - TEMPORAL_ADDRESS: temporal:7233
```

Here, `TEMPORAL_ADDRESS` is declared/written differently from the other options above it and that could cause the issue.

The other syntax of `VAR_NAME: VAR_VALUE` should also work but mixing them both under one `environment` I think confuses Coolify.

<details>
<summary>Kommentartext</summary>

````markdown
I had this issue, and had a hard time understanding what was going on.

Turns out symphony / some php dependency can't parse the docker-compose.yaml file fully.

I think a more long term fix from coolify's side is to swap out the library used to parse docker-compose.yaml files.

Here are changes suggested by chatgpt to fix it, I got it working after implementing them:

## 1 Extended depends_on Objects
Example that triggers the notice
```yaml
depends_on:
  db:
    condition: service_started
    required: true
```

Why it is a problem
Coolify’s PHP parser stores depends_on as a string list. When it receives a mapping (db: {condition:…}) it tries to concatenate that mapping as if it were a string, leading to the warning. In practice Coolify also ignores the condition: logic, so the extra detail buys nothing.

Safer alternative
```yaml
depends_on:
  - db
```

## 2 Long-Form ports, volumes, or networks

Notice-producing form

```yaml
ports:
  - mode: ingress
    target: 80
    published: "8080"
    protocol: tcp
```

Why it is a problem
The PHP helper expects each item to be a scalar (e.g. "8080:80"). Passing a mapping causes the conversion notice and may drop the port from the final container spec.

Safer alternative
```yaml
ports:
  - "8080:80"
```
Apply the same idea to volumes: and service-level networks:.

## 3 Array-Form command or healthcheck.test
Notice-producing form
```yaml
command:
  - sh
  - -c
  - ./entrypoint.sh
```

Why it is a problem
Symfony YAML turns that list into a PHP array. The downstream DTO calls string helpers (trim, explode) on it and emits the notice. In some cases the command is truncated, so the container exits immediately.

Safer alternative
```yaml
command: >-
  sh -c ./entrypoint.sh
The folded scalar (>-) remains readable while satisfying the scalar requirement.
```

## 4 Empty Mapping Stubs {} Notice-producing form
```yaml
volume: {}
```

Why it is a problem
{} is an empty map, which becomes a PHP array. If the value flows into a string context (for example, label templating) Coolify logs the notice. The stub is usually added by formatters but serves no purpose.

Safer alternative
Remove the key entirely.
```yaml
# nothing here; Compose will use defaults
```

The same applies to unused top-level sections such as configs: {} or secrets: {}.

## 5 Implicit Networks and Non-spec restart Values

Notice-producing form

```yaml
restart: never      # non-spec string
networks:
  - coolify-proxy   # declared nowhere; assumed internal
```

Why it is a problem
restart—anything other than "no", "on-failure", "always", or "unless-stopped" is stored as a raw string. The parser later attempts to treat it as a constant and warns.

Networks—if an external network is referenced but not marked external: true, Coolify may create a new internal network instead of joining the proxy, breaking routing.

Safer alternative
```yaml
restart: "no"

networks:
  coolify-proxy:
    external: true
```
````
