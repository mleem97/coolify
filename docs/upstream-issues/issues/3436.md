## Aufarbeitung: IPv6-Clientadressen am Proxy-Eingang korrekt erhalten

**Bereich:** Proxy / Netzwerk · **Priorität:** P1 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

IPv6-Anfragen erreichen Traefik/Caddy auf IPv4-only-Docker-Netzen teilweise mit der Docker-Gateway-Adresse. Dadurch fehlt der Anwendung die echte Client-IP. Der aktuelle Upgrade-Pfad und die Einrichtung verwalteter Server verhalten sich unterschiedlich.

### Reproduktion / Prüfszenario

1. Auf einem kontrollierten Dual-Stack-Host einen Dienst hinter dem Coolify-Proxy bereitstellen.
2. Requests von getrennten IPv4- und IPv6-Clients senden und Peer-IP sowie Forwarded-Header protokollieren.
3. EnableIPv6 des Proxy-Netzes prüfen und das Verhalten mit einem eigens angelegten Dual-Stack-Testnetz vergleichen.

### Befunde

- Der Reporter bestätigt in Kommentar 2613923171, dass ein IPv6-fähiges neu angelegtes coolify-Netz die Client-IP wiederherstellt.
- scripts/upgrade.sh versucht --ipv6 mit Fallback; app/Actions/Server/InstallDocker.php und Server::validateCoolifyNetwork erstellen Standalone-Netze weiterhin ohne --ipv6.
- Neuere Kommentare nennen mehrere PR-Versuche, beweisen aber keinen gemergten vollständigen Fix.

### Umsetzungsschritte

- [ ] Proxy-Eingangsnetz-Erstellung zentralisieren und IPv6 mit geprüftem IPv4-Fallback konsistent anwenden.
- [ ] Bestehende belegte IPv4-Netze erkennen und einen geplanten Migrationspfad anzeigen.
- [ ] Backend-Netze und Swarm-Overlay nicht unbesehen umstellen; Header-Vertrauen nicht pauschal lockern.

### Abnahmekriterien und Regressionstests

- [ ] Dual-Stack-Test liefert die jeweilige externe Client-IP bis zur Anwendung.
- [ ] Hosts ohne IPv6 können weiterhin ein funktionierendes Proxy-Netz erstellen.
- [ ] Bestehende laufende Netze werden nicht automatisch zerstört; eine nötige Migration ist sichtbar.

### Offene Fragen und Risiken

- Netzneuanlage trennt laufende Container und benötigt Wartungsplanung.
- Die Korrektur der Anlage allein migriert keine vorhandenen Installationen.

````markdown
Thanks for this thread. It works when enabling ipv6. This article helped me a lot: https://fariszr.com/docker-ipv6-setup-with-propagation/, so here is what I needed to do:

1. /etc/docker/daemon.json
```
{
  "ipv6": true,
  "fixed-cidr-v6": "2001:db8:1::/64",
  "experimental": true,
  "ip6tables": true,
  "default-address-pools": [
    { "base": "172.17.0.0/16", "size": 16 },
    { "base": "172.18.0.0/16", "size": 16 },
    { "base": "172.19.0.0/16", "size": 16 },
    { "base": "172.20.0.0/14", "size": 16 },
    { "base": "172.24.0.0/14", "size": 16 },
    { "base": "172.28.0.0/14", "size": 16 },
    { "base": "192.168.0.0/16", "size": 20 },
    { "base": 2001:db8:1::/104", "size": 112 }
  ]
}
```
Note that v6 address above must be changed (see referenced docs).

2. Restart docker on host

```
sudo systemctl restart docker
```

3. Recreate all docker networks (this is the painfull step and needs to be planned properly)

- register all currently running containers `export containers=$(docker ps -q)`
- stop all containers (downtime!):  `docker stop $containers`
- list all networks: `docker network ls`
- remove and recreate all networks, one-by-one: `docker network rm $NETWORK && docker network create --ipv6 $NETWORK`

4. Start all containers again

- note. when you do `docker start $conatiner1`, you'll get an error that the network cannot be found, so the newly created networks must be attached
-  this can be done with
```
docker network connect $new-network-id $conatiner1
```
The last step is quite error prone as the shown id relates to a network that is not existing anymore and you need to connect to the correct new network by looking at the network names.

5. Finally start the container with the newly attached network again:
```
docker start $container1
```
and repeat for all containers.

I'll leave automating these steps as an exercise ;-)
````

<summary>Kommentartext</summary>

```markdown
Most of the prs above won’t fully resolve the issue because the problem isn’t global IPv6 support, it’s that only the coolify proxy network needs ipv6, since that’s where traefik receives ingress traffic.

traefik correctly attaches the real client ip only when the ingress network supports ipv6. If that network is ipv4 only, ipv6 clients always appear as Docker internal addresses.

To fix it, the minimal working steps are:
• enable IPv6 in /etc/docker/daemon.json
• restart Docker
• stop all Coolify containers
• remove them from the coolify network
• delete and recreate the coolify network with --ipv6
• reattach containers and redeploy

Alternatively, you can run a host level proxy bound to the host, forward to traefik on a localhost port, and let the host proxy inject the correct headers. In that setup, traefik only needs to trust the host proxy, and docker ipv6 becomes irrelevant.
```
