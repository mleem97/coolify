## Aufarbeitung: CA-Datei bei Updates erhalten, damit laufende Nicht-Root-Container sie weiter lesen können

**Bereich:** TLS, Dateien und Upgrade · **Priorität:** P1 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Der aktuelle CA-Schreibpfad setzt rekursiv restriktive Rechte, löscht die vorhandene CA-Datei und legt sie neu an. Laufende Container mit Datei-Bind-Mount können dadurch weiterhin das alte, unlesbare Dateisystemobjekt sehen. Das passt unmittelbar zur gemeldeten Update-Störung.

### Reproduktion / Prüfszenario

1. CA-Datei read-only in einen laufenden Container mit Nicht-Root-UID einbinden und Dateiinode sowie Lesbarkeit erfassen.
2. CA-Seeder beziehungsweise Upgrade-Pfad ausführen; Zugriff ohne Containerneustart erneut prüfen.

### Befunde

- Meldung und Diskussion erklären, dass ein Neustart des App-Containers den Zugriff wiederherstellt.
- database/seeders/CaSslCertSeeder.php ruft für jeden Server SslHelper::caCertificateFileCommands() auf.
- app/Helpers/SslHelper.php setzt chmod -R 700, führt rm -rf auf coolify-ca.crt aus und schreibt danach die Datei neu.

### Umsetzungsschritte

- [ ] Öffentliche CA-Datei bei vorhandenen Datei-Bind-Mounts in-place aktualisieren, ohne sie zu löschen; gewünschte Dateirechte gezielt setzen.
- [ ] Rekursive Rechteänderung auf Zertifikatsdateien vermeiden und private Schlüssel getrennt schützen.
- [ ] Idempotenten Seeder und Install-/Upgrade-Pfad zusammen prüfen.

### Abnahmekriterien und Regressionstests

- [ ] Ein bereits laufender Nicht-Root-Container liest die CA auch nach erneutem Seeder-Lauf und Upgrade.
- [ ] Dateiinode bleibt für den Datei-Bind-Mount nutzbar; öffentliches Zertifikat erhält die vorgesehenen Leserechte.
- [ ] Private Schlüssel bleiben restriktiv; fehlende Datei oder Verzeichnis wird korrekt und kontrolliert erstellt.

### Offene Fragen und Risiken

- In-place-Schreiben und atomarer Dateiaustausch haben verschiedene Auswirkungen auf bestehende Datei-Bind-Mounts; diese müssen im Test tatsächlich vorhanden sein.
- Die genaue historische Anzeige von UID und Modus beweist allein nicht die Mount-Ursache, der aktuelle Löschpfad ist jedoch direkt belegt.

```markdown
### Error Message and Logs

When a **Dockerfile is configured to run with a non-root user** and a **server CA certificate file is mounted into the container** (`/data/coolify/ssl/coolify-ca.crt:/etc/ssl/certs/coolify-ca.crt:ro`), the **container loses access to this mounted file after a Coolify update or downgrade**. Initially, the file inside the container has permissions like `-rw-r--r-- 1 root root`.

However, after a Coolify update or downgrade, the permissions of `/etc/ssl/certs/coolify-ca.crt` inside the container change to `-rwx------ 0 9999 root`. This **change in permissions and ownership (9999:root)** prevents the non-root user from accessing the file. If I try to `cat /etc/ssl/certs/coolify-ca.crt` after the update/downgrade, I receive the error: `cat: can't open '/etc/ssl/certs/coolify-ca.crt': Permission denied` inside the container. This **issue does not occur when the same Dockerfile is configured to run as the root user (without `USER nonrootuser` )** on the same server, **even though the file's ownership and permissions still change** to `-rwx------ 0 9999 root`. This **behavior is consistent across all connected servers managed by Coolify after update or downgrade the Coolify server**.

### Steps to Reproduce

1.  Set up am application  in Coolify that uses a Dockerfile configured to run as a non-root user (`USER nonrootuser`).
2.  Mount a CA certificate file into the container, for example, using the Coolify UI or `docker-compose.yaml`  on the volume mount: `/data/coolify/ssl/coolify-ca.crt:/etc/ssl/certs/coolify-ca.crt:ro`.
3.  Verify initial permissions and access to the `coolify-ca.crt` file inside the running container (expected: `-rw-r--r--`).
4.  Perform a Coolify update or downgrade through the UI or as described in the [docs](https://coolify.io/docs/get-started/downgrade#_3-execute-the-downgrade-command).
5.  After the Coolify completes the update or downgrade,  check the permissions of `/etc/ssl/certs/coolify-ca.crt` inside the container.
```

```markdown
Yes, I think that is the problem. The 'seeder' runs after pulling the Coolify container (something that is performed during the update process).
After the original file is deleted, the container is left with a broken mount point (**a reference to the inode of the old file**). The strange permissions (`-rwx------ 0 9999 root`) are likely metadata from the parent directory on the host (`/data/coolify/ssl`) 'leaking' through the broken mount.

https://github.com/coollabsio/coolify/blob/abde78094a2b50df769691b944fe040817736162/database/seeders/CaSslCertSeeder.php#L32-L36

A possible fix could be to **avoid deleting the file if it's already present** and instead, overwrite its content.
If that's okay, I could open a pull request with that change. @andrasbacsai @peaklabs-dev
```
