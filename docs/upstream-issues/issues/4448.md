## Aufarbeitung: Build- und Deployment-Server eindeutig zuordnen

**Bereich:** Deployment / Serverwahl · **Priorität:** P1 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Nach Verschieben einer Anwendung soll ein Build auf einem anderen Server Last erzeugt haben. Der Bericht enthält keine Belege für die ausgeführten Remote-Befehle; gemeinsame Hostressourcen und Build-Server-Auswahl müssen von einer falschen Zielzuordnung getrennt werden.

### Reproduktion / Prüfszenario

1. Drei klar getrennte Testhosts als Dashboard, bisheriges Ziel und neues Ziel verwenden.
2. Anwendung mit protokollierter server_id/destination_id löschen und auf dem neuen Ziel anlegen.
3. Deployment ohne und mit dediziertem Build-Server starten und CPU/SSH-Events je Host vergleichen.

### Befunde

- Originalbericht: beta.373, drei VMs mit je 2 GB RAM/2 vCPU; keine Deployment-Logs oder Beispielrepo.
- ApplicationDeploymentJob liest server_id und destination_id aus der Queue und verwaltet mainServer sowie build_server getrennt.
- Aktueller Code enthält eine explizite Build-Server-Kandidatenauswahl und Fallback-Behandlung.

### Umsetzungsschritte

- [ ] Queue-Snapshot, Ressourcen-Ziel und ausgewählten Build-Server im Test abgleichen.
- [ ] Bei bestätigter Verwechslung veraltete Jobs nach Ressourcenwechsel ablehnen oder sichere Zielauflösung korrigieren.
- [ ] Logs sollen benennen, wo gebaut und wo gestartet wird.

### Abnahmekriterien und Regressionstests

- [ ] Ohne Build-Server laufen Build und Start ausschließlich auf dem zugewiesenen Ziel.
- [ ] Mit Build-Server laufen nur die vorgesehenen Schritte dort; Produktionscontainer starten auf mainServer.
- [ ] Ein alter Queueeintrag kann keine neu angelegte Ressource auf einem falschen Host verändern.

### Offene Fragen und Risiken

- CPU-Spitzen allein beweisen keine falsche Serverauswahl.
- Der historische Buildpack ist veraltet; Vergleich mit aktuellem Dockerfile-/Railpack-Pfad erforderlich.
