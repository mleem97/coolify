## Aufarbeitung: Verwaltete Fluent-Bit-Lua-Dateien und begrenzte Logdatei-Mounts ergänzen

**Bereich:** Log Drain / Fluent Bit / Dateiverwaltung · **Priorität:** P2 · **Bewertung:** Erweiterung

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Gewünscht sind zusätzliche Lua-Skripte zur Logtransformation sowie lokale Ausgabeverzeichnisse für Fluent Bit. Der aktuelle eingebaute Logdrain unterstützt nur Konfiguration und Parserdatei; Lua- und File-Plugins werden inzwischen ausdrücklich validierungsseitig ausgeschlossen. Das ist eine neue verwaltete Fähigkeit mit Berechtigungs- und Dateilebenszyklus, kein bloßes Freischalten eines Textfeldes.

### Reproduktion / Prüfszenario

1. Im eingebauten Custom-Logdrain eine harmlose Lua-Filterkonfiguration und einen File-Output konfigurieren und die aktuelle Validierungsantwort dokumentieren.
2. Die generierten Compose-Mounts und bei Neustart neu geschriebenen Dateien prüfen.
3. Die im Kommentar genannte separate Compose-Instanz nur als Vergleich verwenden; Docker-Daemonkonfiguration nicht auf einem produktiven Host ändern.

### Befunde

- Das Issue nennt zwei getrennte Ziele: Lua-Skriptinhalt ähnlich benutzerdefinierten Parsern und Host-Bind-Mounts für File-Output.
- StartLogDrain.php generiert aktuell nur fluent-bit.conf und parsers.conf als read-only gemountete Dateien; der Custom-.env-Inhalt wird leer geschrieben.
- ValidFluentBitConfig::DENIED_PLUGINS enthält ausdrücklich lua und file neben weiteren Plugins. Die gewünschte Fähigkeit liegt somit außerhalb des gegenwärtig unterstützten Konfigurationsumfangs.
- Der Reporter bestätigt eine separate Fluent-Bit-Compose-Instanz als eigenen Workaround, hält aber an einer integrierten Funktion fest.

### Umsetzungsschritte

- [ ] Lua-Dateien als benannte, versionierte Anhänge der Server-Logdrain-Konfiguration speichern und im Container nur lesbar bereitstellen.
- [ ] Für lokale Logausgabe ausdrücklich ausgewählte, verwaltete Verzeichnisse mit nachvollziehbaren Rechten, Pfadprüfung, Rotation und Kapazitätsgrenzen anbieten.
- [ ] Validator und UI nur für diese kontrolliert erzeugten Ressourcen erweitern; ausführbare Filter und Hostschreibzugriff an die passende Serverberechtigung binden.
- [ ] Dateien bei Start, Update, Löschen und Konfigurationsregeneration konsistent behandeln; mit der Credentialdatei-Anforderung aus #7163 abstimmen.

### Abnahmekriterien und Regressionstests

- [ ] Ein Testskript transformiert ein Testlog, bleibt nach Logdrain-Neustart vorhanden und wird nicht in unberechtigten Ansichten offengelegt.
- [ ] File-Output schreibt ausschließlich in das konfigurierte Ziel, mit dokumentierter Rotation und ohne unbegrenzten Plattenverbrauch.
- [ ] Ungültige Datei-/Mountkonfiguration stoppt den aktuell funktionierenden Logdrain nicht.
- [ ] Nutzer ohne entsprechende Serververwaltung können weder Skripte ändern noch Hostpfade freigeben.

### Offene Fragen und Risiken

- Lua und Hostdateiausgabe erweitern bewusst den Funktionsumfang; die bisherige Sperrliste darf nicht still entfernt werden.
- Die getrennte Fluent-Bit-Compose-Lösung ist ein möglicher Expertenweg, aber kein Beleg für eine fertige native Integration.
- Ressourcen-, Server- und Teamrechte müssen gemäß SECURITY.md am tatsächlichen Zielserver geprüft werden.

### Request Type

New Feature

### Description

Using the Fluent Bit logging feature works fine, as long as we do not need custom lua script support or want to store the logs on the local host machine.

Therefore, I would like to request:

1) Custom Lua scripts for advanced log parsing, transformation, and enrichment; could be implemented analog to the current existing custom parser functionality.

2) Host system bind mounts to support File Output type. Simple systems may only want to dump the log files on the host machine; this is currently not possible with the built-in Log Drain functionality.

### Current Behavior
We can enable Log Drain for the Host machine, but neither custom Lua scripts nor the File Output type can be used properly.

### Expected Behavior
I can define custom LUA scripts as I can define custom parsers.
I can define local directory bind mounts to "dump" logs to the host machine.
