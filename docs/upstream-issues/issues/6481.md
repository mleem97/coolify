## Aufarbeitung: Commitmetadaten im übergeordneten Repository statt im Submodul lesen

**Bereich:** Git / Submodule / Deployment · **Priorität:** P2 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Liegt das konfigurierte Basisverzeichnis innerhalb eines Git-Submoduls, wird die Commitnachricht des Hauptrepositorys im falschen Git-Repository gesucht. Der aktuelle Deploymentjob verwendet dafür weiterhin workdir, obwohl dieses Verzeichnis um base_directory erweitert wurde.

### Reproduktion / Prüfszenario

1. Ein Hauptrepository mit einem Submodul anlegen; den Parent-Commit so wählen, dass dessen SHA im Submodul nicht existiert.
2. Submodule aktivieren und base_directory auf den Submodulpfad setzen; ein Deployment starten.
3. Denselben Build aus einem gewöhnlichen Unterverzeichnis und aus dem Repository-Root vergleichen.

### Befunde

- Originalmeldung zu beta.424 beschreibt den fehlenden Parent-SHA im Submodul; der einzige Kommentar kündigt eine Korrektur an, ohne einen überprüfbaren PR zu verlinken.
- ApplicationDeploymentJob konstruiert basedir als Clone-Verzeichnis und workdir als basedir plus base_directory.
- clone_repository() führt nach dem Import weiterhin cd workdir && git log -1 <Parent-Commit> --pretty=%B aus. Git wechselt dadurch bei einem Submodul in dessen eigene Historie.
- Die inzwischen vorhandene Submodulbehandlung beim Laden von Compose-Dateien in Application.php betrifft einen anderen Ablauf und beseitigt diesen Metadatenzugriff nicht.

### Umsetzungsschritte

- [ ] Commitnachricht und andere auf den Parent-Commit bezogene Metadaten explizit im basedir abfragen, vorzugsweise mit klarer git -C-Zuordnung.
- [ ] Buildkontext weiterhin im workdir belassen; Parent- und Submodulrevision nicht gleichsetzen.
- [ ] Einen Regressionstest mit zwei tatsächlich getrennten lokalen Git-Historien ergänzen; auch verschachtelte Unterverzeichnisse abdecken.

### Abnahmekriterien und Regressionstests

- [ ] Eine Anwendung im Submodul wird mit dem vom Hauptrepository referenzierten Submodulstand gebaut.
- [ ] Die Deploymenthistorie zeigt die Nachricht des ausgelösten Parent-Commits.
- [ ] Normale Monorepo-Unterverzeichnisse sowie Root-Builds behalten ihre bisherigen Metadaten.

### Offene Fragen und Risiken

- Der falsche Verzeichnisbezug ist statisch nachgewiesen; ein vollständiges Deployment wurde nicht gestartet.
- Zugriffsrechte auf private Submodule und Git-LFS sind davon unabhängige Voraussetzungen.
