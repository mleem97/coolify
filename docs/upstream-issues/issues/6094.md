## Aufarbeitung: Chaskiq-Vorlage mit kontrollierter Initialisierung und gültiger WebSocket-URL bereitstellen

**Bereich:** Servicevorlagen · **Priorität:** P2 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Eine unveränderte Chaskiq-Installation liefert HTTP 500. Die Vorlage nutzt ein bewegliches latest-Image; in ihr stehen ein exec vor Initialisierungsschritten und eine zusammengesetzte WS-Adresse mit SERVICE_URL, die bereits ein Scheme enthält. Diese konkreten Prüfpunkte sind von der unbewiesenen 500-Ursache zu trennen.

### Reproduktion / Prüfszenario

1. Chaskiq mit leeren Volumes und unveränderter Vorlage starten; verwendeten Image-Digest sichern.
2. HTTP-Aufruf, Rails-Initialisierung, Datenbankmigration, Sidekiq-Start und erzeugte Host-/WS-Variablen getrennt prüfen.

### Befunde

- Erstbericht beta.420.1 und ein späterer Kommentar bestätigen HTTP 500 ohne aussagekräftige Konsolenlogs.
- templates/compose/chaskiq.yaml verwendet chaskiq/chaskiq:latest, einen eingebundenen entrypoint und WS=wss://${SERVICE_URL_CHASKIQ}/cable.
- bootstrap/helpers/parsers.php unterscheidet SERVICE_URL mit Scheme von SERVICE_FQDN ohne Scheme; exec "$@" steht im Template vor db:setup/db:migrate.

### Umsetzungsschritte

- [ ] Unterstützten Chaskiq-Image-Stand und dessen CMD/ENTRYPOINT feststellen, bevor das Init-Skript geändert wird.
- [ ] Migrationen idempotent vor dem endgültigen exec ausführen und Fehler sichtbar machen; kein pauschales Unterdrücken fehlgeschlagener Initialisierung.
- [ ] WebSocket-URL aus Scheme und Host korrekt ableiten, anschließend Healthcheck und Sidekiq-Abhängigkeit prüfen.

### Abnahmekriterien und Regressionstests

- [ ] Frische Installation erreicht Login/Startseite ohne HTTP 500.
- [ ] Neustart mit vorhandenen Volumes erzeugt keinen zweiten Admin und beschädigt keine Daten.
- [ ] WebSocket-Verbindung und Hintergrundjobs funktionieren; Fehler beim Setup erscheinen ohne Secret-Ausgabe.

### Offene Fragen und Risiken

- Der Report enthält keinen Rails-Stacktrace; ein Templateverdacht ersetzt die Laufzeitreproduktion nicht.
- Bei exec ohne Argumente ist das Verhalten anders als bei geerbtem Image-CMD; deshalb Image-Metadaten einbeziehen.
