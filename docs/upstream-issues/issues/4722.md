## Aufarbeitung: Domains für Compose-Dienste mit Inline-Dockerfile speichern

**Bereich:** Compose / Oberfläche · **Priorität:** P2 · **Bewertung:** Möglicherweise bereits adressiert

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Ein Dienst ohne explizites image, aber mit build.dockerfile_inline, konnte im alten Formular keine Domainänderung speichern. Die aktuelle Domainverwaltung ist von der Imageeingabe getrennt; die damalige Browser-required-Sperre ist dort nicht mehr erkennbar.

### Reproduktion / Prüfszenario

1. Dienst mit build.dockerfile_inline und ohne image anlegen und bauen.
2. Auf der heutigen Domains-Seite eine Domain ergänzen und ändern.
3. Nach erneutem Compose-Speichern und Neustart denselben Ablauf wiederholen.

### Befunde

- Das historische HTML-Formular fordert ein Image, obwohl der Build das Image erzeugt.
- app/Livewire/Project/Service/Domains.php bearbeitet Domainlisten und enthält keine required-Imagevalidierung in diesem Save-Pfad.
- Der aktuelle Compose-Parser kann für Build-Dienste ohne Image einen eigenen Tag erzeugen.

### Umsetzungsschritte

- [ ] Den Fall in aktueller Service-/Domainverwaltung reproduzieren, bevor eine neue Imagepflicht geändert wird.
- [ ] Falls noch ein Altformular blockiert, image nur verlangen, wenn weder build noch dockerfile_inline einen Build liefern.
- [ ] Inline-Build und generierten Image-Tag in der Oberfläche verständlich darstellen.

### Abnahmekriterien und Regressionstests

- [ ] Domainänderung gelingt ohne erfundenen Imagewert.
- [ ] Inline-Dockerfile wird weiterhin gebaut und der Dienst erhält den richtigen Proxy-Port.
- [ ] Reines image-basiertes Deployment behält seine Validierung.

### Offene Fragen und Risiken

- Ein generierter Tag und ein vom Benutzer vorgegebenes Image haben unterschiedliche Update-Semantik.
