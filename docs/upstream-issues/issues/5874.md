## Aufarbeitung: OpenAPI-Schema der Deployment-Liste an die tatsächliche Antwort anpassen

**Bereich:** API und Dokumentation · **Priorität:** P2 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Das Schema des Endpunkts für Anwendungsdeployments beschreibt weiterhin ein Array von Applications. Tatsächlich liefert der Controller ein Objekt mit count und deployments; auch der Elementtyp ist falsch. Die Abweichung ist im geprüften Code direkt sichtbar.

### Reproduktion / Prüfszenario

1. GET /api/v1/deployments/applications/{uuid}?take=2 mit autorisiertem Lesetoken abrufen.
2. Antwortstruktur mit der OpenAPI-Annotation von get_application_deployments vergleichen.

### Befunde

- app/Http/Controllers/Api/DeployController.php: Annotation bei get_application_deployments verwendet type=array und Items(Application).
- app/Models/Application.php: deployments() gibt count und deployments zurück; der Controller serialisiert dieses Objekt direkt.
- Kommentar vom 01.05.2026 benennt beide Abweichungen und verweist auf frühere unvollständige PRs.

### Umsetzungsschritte

- [ ] Antwortschema als Objekt mit integer count und Array<ApplicationDeploymentQueue> definieren.
- [ ] Generierte OpenAPI-Artefakte mit dem vorgesehenen Projektkommando aktualisieren.
- [ ] Vertragstest ergänzen, der Dokumentation und reale leere beziehungsweise gefüllte Antworten abgleicht.

### Abnahmekriterien und Regressionstests

- [ ] Generierter Client erwartet {count, deployments:[...]} und den Deployment-Typ.
- [ ] Leere Liste, Pagination und fehlende Anwendung sind korrekt dokumentiert.
- [ ] Logs und sensible Felder bleiben abhängig von Tokenberechtigungen redigiert.

### Offene Fragen und Risiken

- Die API-Antwort nicht an die bisher falsche Dokumentation angleichen; das würde bestehende Clients brechen.
- PR-Verweise in Kommentaren belegen allein keinen Merge in diesen Fork.

````markdown
Adding a finding from a downstream client fix — this issue's scope is bigger than the item-ref swap. There are **two** mismatches between the OA annotation and the real response:

**1. Item type** (already covered above) — `items` should be `ApplicationDeploymentQueue`, not `Application`.

**2. Outer shape** (not yet flagged) — the annotation declares a top-level array, but the controller returns an envelope. From `app/Models/Application.php:1056-1071`:

```php
public function deployments(int $skip = 0, int $take = 10, ?string $pullRequestId = null)
{
    // ...
    return [
        'count' => $count,
        'deployments' => $deployments,
    ];
}
```

And `DeployController::get_application_deployments` returns that directly via `response()->json($deployments)`.

Verified live against `v4.0.0-beta.472`:

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  "$COOLIFY/api/v1/deployments/applications/$APP_UUID?take=2" | jq 'keys'
# => ["count", "deployments"]
```

So the closed PRs (#9733, #9764, #9768) only fix half the problem — they correct `items` but leave the outer `type: 'array'` declaration, which still doesn't match the real `{ count, deployments: [...] }` envelope.

A complete annotation should look roughly like:

```php
schema: new OA\Schema(
    type: 'object',
    properties: [
        new OA\Property(property: 'count', type: 'integer'),
        new OA\Property(
            property: 'deployments',
            type: 'array',
            items: new OA\Items(ref: '#/components/schemas/ApplicationDeploymentQueue'),
        ),
    ],
)
```

Then regenerate `openapi.yaml` / `openapi.json`.

Reference / downstream fix: we hit this in an MCP client and worked around it by parsing the envelope and tolerating malformed responses — https://github.com/StuMason/coolify-mcp/pull/158 (merged). Smoke-tested against `v4.0.0-beta.472`.

Happy to send a PR upstream covering both axes (annotation + regenerated specs + regression test) if a maintainer can confirm the envelope shape is intended and stable.
````
