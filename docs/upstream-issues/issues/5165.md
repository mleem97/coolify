## Aufarbeitung: Build-Kontext und dockerignore bei generierten Buildpacks erklären

**Bereich:** Build / Entwicklererlebnis · **Priorität:** P3 · **Bewertung:** Integration / Dokumentation

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Eine bestehende dockerignore-Allowlist schließt Dateien aus, die ein generiertes Buildpack zum Build benötigt. Der Bericht erwartet zusätzlich einen gut erreichbaren Checkout in Hooks. Das sind Kontext-/Workflow-Fragen; pauschales Entfernen von dockerignore kann Geheimnisse in Images bringen.

### Reproduktion / Prüfszenario

1. Testrepo mit restriktiver dockerignore-Allowlist und bewusst ausgeschlossener Testdatei verwenden.
2. Den vorhandenen Alt-Buildpack-Fall dokumentieren und denselben Build mit explizitem Dockerfile beziehungsweise Railpack prüfen.
3. Prüfen, welche generierten Hilfsdateien und Checkout-Pfade der jeweilige Build wirklich benötigt.

### Befunde

- Originalbericht: beta.390, Ausschlussmuster * und fehlende generierte Builddateien.
- AGENTS.md kennzeichnet Nixpacks am geprüften Stand als deprecated.
- ApplicationDeploymentJob enthält getrennte generierte Buildkonfigurationen und Dockerfile-Pfade.

### Umsetzungsschritte

- [ ] Für neue Konfigurationen einen expliziten Dockerfile-Build oder passenden Railpack-Workflow dokumentieren.
- [ ] Fehlende generierte Builddateien mit einer konkreten Fehlermeldung identifizieren.
- [ ] Hook-Arbeitsverzeichnis und Preserve-Repository-Verhalten erklären, ohne dockerignore automatisch zu deaktivieren.

### Abnahmekriterien und Regressionstests

- [ ] Build-Kontext enthält nur ausdrücklich erwartete Dateien.
- [ ] Eine ausgeschlossene Geheimnis-Testdatei gelangt nie ins Image.
- [ ] Fehler nennt die benötigte Datei und die wirksame Ignore-Regel beziehungsweise Kontextgrenze.

### Offene Fragen und Risiken

- Ein CI-System kann absichtlich ausgeschlossene Quelldateien nicht korrekt bauen.
- Das alte Buildpack sollte nicht Grundlage neuer Funktionsentwicklung werden.

### Error Message and Logs

I am migrating PR previews to Coolify from Vercel. The project has some existing docker container setup and `.dockerignore` file, all unrelated to Coolify. The `.dockerfile` is written in the form of an allowlist:

```
*
!/my/file
!/another/file
```

This restricts docker (dev and prod) from seeing anything that I don't want it too see. It also reduces build times, because the project is big and there is no point to copy the entire thing into docker context every time (`COPY` commands operate not on the actual files, but on their copies stashed somewhere in docker internals, called "docker context"; this copying is performed as the first step when you run `docker build`).

Instead, my dev containers use volumes (`--volume`) to give access to the selected directories and the project build runs during `docker run` stage. My prod containers are very simple and only copy some prebuilt artifacts whitelisted as a single directory in the `.dockerignore`.

However, Nixpacks deployments use `COPY` commands to bring the project files into the container image and then run the build during the `docker build` phase. Not only it's a waste of time and disk space, but it also trips on the `.dockerignore`, unless all project files and some special Nixpacks directories such as `.nix` or `./nginx.conf` are allowed.

This requires me to modify my project's existing docker setup, and/or to pollute the project with unnecessary details of Coolify internal workings.


A few possible solutions I see:
 1. Give more control over the project files between code checkout and when deployment containers start running: for example, I could `rm .dockerignore` in advance to make Nixpacks happy. The pre-deployment script does not work for me, because I cannot find where my project files are. I think it might be running before checkout?
 2. Allow mounting directories as volumes rather than `COPY`ing the entire thing into the images. IIUC, this cannot be easily changed for Nixpacks. But at least give possibility to do this in other build packs, such as static, docker and docker-compose.
 3. While I could (and am trying to) setup a custom `docker-compose.yaml`, where I mount the volume, run build "service", then "static server" service, I cannot figure out how to find the project dir to mount it, because the project dir path is non-deterministic and is not exposed anywhere (e.g. as an env var). Coolify could provide an env var which contains path to the checked out project so that I could mount it into a service inside `docker-compose.yaml`.


This are all particularities, but in general:
 - I would expect CI service to run no matter what I have in my project. My files cannot make the CI server to break internally.
 - I would expect that the project directory should be easily accessible and be the working directory by default on every stage of the CI run.


This is the default experience of every CI service and I would like Coolify to also implement that behavior.


### Steps to Reproduce

1. Have a `.dockerignore` file in your repo, containing `*`
2. Try to run a deployment of any shape or form
3. Observe deployment fails because it cannot see project files or even `.nix` directory
