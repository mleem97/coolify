# Upstream #6122: Lokale Docker-Images ohne erzwungenen Registry-Pull deployen

## Aufarbeitung: Lokale Docker-Images ohne erzwungenen Registry-Pull deployen

**Bereich:** Docker-Images · **Priorität:** P2 · **Bewertung:** Konkreter Codebefund

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Ein auf dem Zielhost vorhandenes und direkt startbares Image scheitert in Coolify, weil der Docker-Image-Buildpack einen Registry-Pull ausführt. Im aktuellen Startpfad ist dieser Pull für normale Image-Deployments weiterhin vorgesehen.

### Reproduktion / Prüfszenario

1. Ein eindeutiges Testimage lokal auf dem Zielserver laden, das in keiner erreichbaren Registry existiert.
2. Als Docker-Image-Ressource deployen und Pull-Fehler mit einem direkten lokalen Containerstart vergleichen.

### Befunde

- Meldung beta.420.1 und Kommentare erklären den Unterschied zwischen lokalem Imagebestand und Remote-Registry.
- ApplicationDeploymentJob::start_by_compose_file() führt bei dockerimage ohne bereits gepinntes Scan-Image docker compose pull aus.
- deploy_dockerimage_buildpack() besitzt im geprüften Pfad keine ausdrückliche Local-image-Auswahl.

### Umsetzungsschritte

- [ ] Explizite Image-Pull-Policy mit klarer Semantik für always, if-missing und never beziehungsweise lokalen Betrieb vorsehen.
- [ ] Vor einem Local-image-Deployment das Image auf jedem tatsächlichen Zielserver prüfen; bei Fehlen vor dem Stoppen alter Container abbrechen.
- [ ] Policy durch Image-Scanning, Rollback und zusätzliche Server konsistent weiterreichen.

### Abnahmekriterien und Regressionstests

- [ ] Local/never startet das vorhandene Image ohne Registry-Netzwerkzugriff.
- [ ] Fehlendes lokales Image erzeugt einen verständlichen Fehler und erhält die laufende Version.
- [ ] Standard-Registry-Deployments aktualisieren Images weiterhin entsprechend ihrer gewählten Policy.

### Offene Fragen und Risiken

- Lokale Tags sind je Docker-Host unterschiedlich und können zwischen Servern divergieren.
- Das Schreiben eines Image-Namens mit localhost allein erzeugt keine lokale Pull-Policy.
