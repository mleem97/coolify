## Aufarbeitung: Mehrere GitHub-App-Installationen in der Quellenwahl unterstützen

**Bereich:** Git-Quellen / GitHub · **Priorität:** P2 · **Bewertung:** Erweiterung

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Ein GitHub-App-Datensatz enthält weiterhin eine einzelne installation_id. Mehrere Installationen derselben App können heute als getrennte Quellen behandelt werden; der gewünschte zentrale Account-/Installationswechsler ist damit noch nicht als vorhanden belegt.

### Reproduktion / Prüfszenario

1. Dieselbe Test-GitHub-App in einem persönlichen Account und einer Organisation installieren.
2. Beide Installationen mit getrennten Repositoryfreigaben in Coolify anbinden.
3. Anwendungen beider Accounts erstellen und Webhooks sowie Tokenausstellung prüfen.

### Befunde

- Originalbericht und Kommentare beschreiben das Überschreiben beziehungsweise manuelle Wechseln der installation_id.
- GithubApp besitzt weiter ein einzelnes installation_id-Feld.
- tests/Feature/GithubAppMultipleInstallationsWebhookTest.php testet ausdrücklich zwei Quellen derselben app_id mit unterschiedlichen Installations-IDs.

### Umsetzungsschritte

- [ ] Die bereits mögliche Mehrquellenlösung sichtbar und eindeutig nach Account darstellen.
- [ ] Für eine zentrale Appverwaltung Installationen als eigene zugeordnete Entitäten planen.
- [ ] Token und Repositoryliste immer anhand der ausgewählten Installation und des Ressourcenteams auflösen.

### Abnahmekriterien und Regressionstests

- [ ] Beide Account-Repolisten sind ohne manuelles Überschreiben einer aktiven Quelle auswählbar.
- [ ] Bestehende Anwendungen behalten ihre Installation und funktionieren nach Hinzufügen einer zweiten weiter.
- [ ] Deinstallierte oder eingeschränkte Installationen erzeugen einen erklärten Zustand statt 500.

### Offene Fragen und Risiken

- Ein UI-Dropdown allein genügt nicht, wenn Datenmodell, Cache und Webhookrouting weiterhin nur eine Installation erwarten.
- Teamgrenzen und App-Private-Key-Nutzung müssen erhalten bleiben.

```markdown
I did something similar to @rafadc. I can't keep changing the installation ID because, presumably, other deployments will stop working. Instead, I created new GitHub Apps in Coolify for each additional org. I reused the same app details from the first app I created through Coolify. The steps I went through were:
1. Clicked "+ Add" on Sources page
2. On the next page (where it lets you select the endpoint), I clicked on the button that says "Continue" under manual installation
3. Over there, I copied the App ID, Client ID, Client Secret, and Webhook secret, and set the private key that was created for the first app
4. I also set the organization name to the one I want
5. On GitHub, I then manually installed the application to the organization I wanted
6. Be careful here, as GitHub will redirect to the first app you created (because of the URL configured with the app)
7. I then get the installation id from the URL and put it in Coolify's app

This works functionally, but the experience is somewhat poor. I give a separate app name on Coolify from the one in the Github app to distinguish the different sources. This is especially required on pages such as where we add resources, because it does not show the organization in that display. It will just end up showing a bunch of apps with the same name.

In such a setup, if I click on links such as "Rename" or "Update Repositories" on the Source page, it prefixes the app name as defined in Coolify and ends up at a 404. In my case, I typically give access to all repositories because it's an internal app and I don't have much use for these links, so I can live with this.
```
