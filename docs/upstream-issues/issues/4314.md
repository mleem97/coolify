## Aufarbeitung: Neustart-Logs hinter Caddy und vorgeschaltetem Proxy erhalten

**Bereich:** Proxy / Livewire · **Priorität:** P2 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Beim Neustart eines Dienstes bricht der Livewire-Aufruf zum Logfenster mit 502 ab. Die dokumentierte Kette enthält zusätzlich NGINX vor Caddy; dass dieser zusätzliche Hop irrelevant sei, ist eine Vermutung des Reporters.

### Reproduktion / Prüfszenario

1. Einen Testdienst über die Kette Browser → NGINX → Caddy → Coolify neu starten.
2. Gleichzeitig Livewire-Request, WebSocket-Verbindung und Logs beider Proxys verfolgen.
3. Dasselbe direkt über Caddy und direkt zum Dashboard testen.

### Befunde

- Das zitierte NGINX-Log zeigt upstream prematurely closed connection für POST /livewire/update.
- Es liegen keine weiteren Kommentare oder ein minimaler Proxy-Configsatz vor.
- app/Livewire/Project/Service/Heading.php und app/Actions/Service/RestartService.php sind aktuelle Neustart-Einstiegspunkte.

### Umsetzungsschritte

- [ ] Prüfen, ob ein Dienstneustart unnötig den Dashboard-Proxy neu startet oder nur eine Verbindung beendet.
- [ ] Neustartstatus unabhängig vom ursprünglichen Request wieder abrufbar halten.
- [ ] Bei nachgewiesenem Fehler gezielt Reload-/WebSocket-Behandlung korrigieren.

### Abnahmekriterien und Regressionstests

- [ ] Dienstneustart zeigt Abschluss oder Fehler auch nach kurzer Verbindungsunterbrechung.
- [ ] Kein unbegründeter Dashboard-Proxy-Neustart.
- [ ] Direkter und zweifach geproxter Zugriff liefern konsistente Ergebnisse.

### Offene Fragen und Risiken

- NGINX-Timeouts und WebSocket-Header sind unbekannt.
- Aus einer 502-Antwort folgt nicht automatisch eine Caddy-Fehlfunktion.
