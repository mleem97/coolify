# Upstream #6325: Bestehende WebSocket-Verbindungen während des Deployment-Builds erhalten

## Aufarbeitung: Bestehende WebSocket-Verbindungen während des Deployment-Builds erhalten

**Bereich:** Caddy / WebSockets / Rolling Deployment · **Priorität:** P1 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Eine Bun-/Socket.IO-Anwendung verliert laut Bericht bereits beim Beginn eines neuen Builds ihre WebSocket-Verbindungen, obwohl der alte Container weiterläuft. Erst nach Fertigstellung der neuen Version gelingt der Verbindungsaufbau wieder. Das ist vom erwartbaren Austausch des alten Containers am Ende des Deployments zu trennen.

### Reproduktion / Prüfszenario

1. Mit einer kleinen Socket.IO-Anwendung dauerhaft verbundene Clients und einen absichtlich langen Build verwenden; einen Zeitstrahl für Buildstart, Proxyreload, Containerstart und Healthcheck aufnehmen.
2. Direkten Containerzugriff mit Zugriff über Caddy vergleichen; bestehende und neu aufgebaute Verbindungen getrennt zählen.
3. Erfolgreichen und absichtlich fehlgeschlagenen Healthcheck der neuen Version testen; Hostport-Mappings, feste Containernamen und Vorschau-Deployment als gesonderte Betriebsarten behandeln.

### Befunde

- Originalmeldung zu beta.420.6 beschreibt Disconnects unmittelbar beim Start des Builds, obwohl Healthchecks konfiguriert sind und der alte Container noch läuft.
- bootstrap/helpers/docker.php generiert inzwischen Caddy reverse_proxy.stream_close_delay; bootstrap/helpers/constants.php setzt dafür 24h. Das adressiert eine mögliche Reload-Ursache, belegt aber keine Lösung dieses Falls.
- ApplicationDeploymentJob::rolling_update() startet im regulären Rolling-Pfad zunächst den neuen Container, wartet auf health_check() und Proxybereitschaft und stoppt anschließend die alte Version.
- Bei Hostport-Mappings, konsistentem Containernamen, Vorschauen oder festen IP-Adressen wird dieser Rolling-Pfad ausdrücklich umgangen.

### Umsetzungsschritte

- [ ] Proxykonfigurationsänderungen während der Buildphase nachweisen und unnötige Änderungen vor Bereitstellung der neuen Version vermeiden.
- [ ] Den Lebenszyklus bestehender WebSockets beim Caddy-Reload und bei der Containerablösung mit dokumentiertem Drain-Verhalten absichern.
- [ ] Falls frühes Routing die Ursache ist, neue Upstreams erst nach Bereitschaft erreichbar machen; Hinweise für Betriebsarten ohne Rolling-Update ergänzen.

### Abnahmekriterien und Regressionstests

- [ ] Während eines langen oder fehlgeschlagenen Builds bleiben alte Version und bestehende WebSocket-Verbindungen erreichbar.
- [ ] Neue Verbindungen werden erst an die neue Version geleitet, wenn deren Healthcheck erfolgreich ist.
- [ ] Der endgültige Containerwechsel folgt einer nachvollziehbaren Drain-/Reconnect-Regel; keine pauschale Zusage unbegrenzter Socketlebensdauer.

### Offene Fragen und Risiken

- Keine vollständige Proxykonfiguration, genaue Socket.IO-Version oder Laufzeitaufzeichnung vorhanden.
- Caddy-Reload, Docker-Netzwerk und App-Verhalten sind getrennte Hypothesen; die statische Prüfung entscheidet nicht zwischen ihnen.

I'm deploying a Bun + Express server using Socket.IO on Coolify, with deployments handled via Docker and Caddy as the reverse proxy.

Whenever I push new code and a deployment is triggered, all previously connected WebSocket clients are immediately disconnected, even though the existing container is still running. Clients are then unable to reconnect until the new container is fully built and ready, causing significant downtime and poor user experience.

This happens even with health checks configured, suggesting that traffic is being prematurely routed to the new container before it's ready, and the old container is either being drained too early or socket traffic is forcibly cut.

Expected Behavior
Existing WebSocket connections should remain alive during the build phase of a new deployment.

Traffic should continue to route to the old container until the new one passes health checks and is confirmed ready.

WebSocket clients should not experience disconnects or transport errors during this process.



### Steps to Reproduce
Set up a Bun + Express server with Socket.IO and Redis adapter
Deploy the server on Coolify using Docker and Caddy as the reverse proxy
Open a web client and establish an active WebSocket connection to the deployed server
Push a new code change to trigger a new deployment in Coolify

Observe that:
All connected clients are disconnected immediately
Clients fail to reconnect until the new container is fully built and running
