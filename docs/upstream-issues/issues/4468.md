## Aufarbeitung: Relative Compose-Pfade an der richtigen Basis auflösen

**Bereich:** Compose / Dateispeicher · **Priorität:** P2 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Compose-Dateien in Unterordnern können relative Bind-Mounts fälschlich am Projektroot auflösen. Zusätzlich nennt der Bericht eine abweichende Standard-Restart-Policy für Einmaljobs; das sind zwei separat zu testende Verhaltensweisen.

### Reproduktion / Prüfszenario

1. Repo mit Compose-Datei unter deploy/docker und einer danebenliegenden Konfigurationsdatei anlegen.
2. Base Directory und Compose Location getrennt konfigurieren, dann relative kurze und lange Bind-Mounts deployen.
3. Einen Migrationsdienst mit explizitem restart: no sowie ohne Restart-Angabe vergleichen.

### Befunde

- Der Bericht nennt konkrete Soll-/Ist-Pfade bei SigNoz.
- Ein späterer Kommentar verweist auf ein eigenes SigNoz-Template; das beweist keine allgemeine Pfadkorrektur.
- ApplicationDeploymentJob setzt --project-directory explizit; LocalFileVolume und Parser besitzen inzwischen eigene Pfadauflösung und Tests.

### Umsetzungsschritte

- [ ] Gewünschte Compose-Semantik für Base Directory und Compose Location festschreiben.
- [ ] Parsing, Kopieren des Checkouts und docker compose mit derselben Basis ausführen.
- [ ] Dateimounts von Verzeichnissen unterscheiden und die Restart-Policy-Frage separat absichern.

### Abnahmekriterien und Regressionstests

- [ ] Konfigurationsdateien werden vom erwarteten Unterordner gemountet, nicht als leere Verzeichnisse erzeugt.
- [ ] Preview- und normale Deployments lösen dieselbe Struktur korrekt auf.
- [ ] Einmaljobs mit restart: no werden nicht dauerhaft neu gestartet.

### Offene Fragen und Risiken

- Ein pauschales Verschieben aller Dateien ins Root wäre ein Workaround mit Wartungsaufwand.
- Das aktuelle SigNoz-Template löst nicht automatisch den generischen Fall.

````markdown
### Error Message and Logs

Hello

I am trying to deploy a [self-hosted version of Signoz](https://signoz.io/docs/install/docker/) to my Coolify instance.
The self-host process consists of cloning the git repository and use a docker-compose file that is inside a subdirectory.
While the Coolify project's dashboard allows us to point to a custom docker-compose file, the location of the relative paths that are defined for the volumes are relative to the repository's root instead of the docker-compose file location, leading to errors while mounting the volumes.

### Steps to Reproduce

1. Create a new application on coolify that uses the [Signoz repo](https://github.com/SigNoz/signoz)
2. Set the build pack to "Docker Compose"
3. Set the docker-compose location to `/deploy/docker/clickhouse-setup/docker-compose-minimal.yaml`

The computed docker-compose file will consider that the docker-compose file's directory is the root directory, while this should not be the case.

For example, we have

```
volumes:
      - '/data/coolify/applications/vs4ksookkc8skg0ckkw0o4wc/clickhouse-config.xml:/etc/clickhouse-server/config.xml'
 ```

which should actually be

```
volumes:
      - '/data/coolify/applications/vs4ksookkc8skg0ckkw0o4wc/deploy/docker/clickhouse-setup/clickhouse-config.xml:/etc/clickhouse-server/config.xml'
 ```

This causes errors when mounting the volumes during the deploy, because it tries to mount a volume on something that does not exist.

### Example Repository URL

https://github.com/SigNoz/signoz

### Coolify Version

v4.0.0-beta.373

### Are you using Coolify Cloud?

No (self-hosted)

### Operating System and Version (self-hosted)

Debian 10

### Additional Information

I should also note that the default restart policy, when it's not mentioned for a container, is set to `unless-stopped`, which is not the same as the docker-compose default one which is "no". Maybe we should be able to have some control on this for each container, because this also breaks some containers for signoz which are migration tasks that needs to run before the whole stuff runs.
````

```markdown
@foyarash i think you will get a lot of errors, even if this worked as coolify compose need to be parsed first, so the file volume mounts end up being treated as directories unless you specify type bind.

Even ticking preserve repository during deployment might not give you the correct file binds (due to coolify parsing the compose and creating one at root of project)

when using a compose you currently always need to make it work with coolify first, so in the above example if youre cloning the repo, then you have to edit the entire compose to make it work, a lot of service templates inclue the config file contents inside the compose, removing the need for 'repo' file binds

this is a tough one to solve, with how coolify currently works
```
