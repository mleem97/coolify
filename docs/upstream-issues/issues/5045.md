## Aufarbeitung: Vaultwarden-Adminhash unverändert durch die ENV-Verarbeitung führen

**Bereich:** Service-Template / Secrets · **Priorität:** P1 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Dollarzeichen eines Argon2id-Adminhashes wurden in ADMIN_TOKEN durch wechselnde Zahlen ersetzt. Dieses Muster passt zu zusätzlicher Shell-Expansion; es ist mit einem synthetischen Hash zu prüfen. Das Hashformat oder die Passwortstärke sollte nicht als Workaround verändert werden.

### Reproduktion / Prüfszenario

1. Vaultwarden-Teststack mit synthetischem Argon2id-Hash in der vorgesehenen Variable konfigurieren.
2. Einfaches $, literal $$ und Literal-Modus jeweils über die dokumentierte Eingabeform testen.
3. Wert im finalen Container byteweise mit dem Ausgangswert vergleichen und eine Testanmeldung durchführen.

### Befunde

- Der Reporter beschreibt wechselnde numerische Ersetzungen und eine Differenz zwischen SERVICE_PASSWORD_64_ADMIN und ADMIN_TOKEN.
- templates/compose/vaultwarden.yaml referenziert ADMIN_TOKEN weiterhin über die generierte Variable.
- ApplicationDeploymentJob und EnvironmentVariable besitzen inzwischen besondere Shell-/dotenv-Escaping-Pfade.

### Umsetzungsschritte

- [ ] Jede Expansion zwischen UI, gespeicherter Variable, Shell, dotenv und Compose nachverfolgen.
- [ ] Genau eine definierte Expansion je Format erlauben; Nutzereingaben nicht manuell doppelt escapen lassen.
- [ ] Einen Regressionstest mit vollständigem synthetischem Hash und weiteren Dollar-/Quotezeichen ergänzen.

### Abnahmekriterien und Regressionstests

- [ ] ADMIN_TOKEN entspricht exakt dem gespeicherten Hash.
- [ ] Nach Neustart bleibt der Wert unverändert und die richtige Testpassphrase funktioniert.
- [ ] Weder Hash noch Token erscheinen in Diagnose- oder Deploymentlogs.

### Offene Fragen und Risiken

- Kommentare empfehlen Hardcoding in Compose; das würde Secrets unnötig in Konfigurationshistorien verbreiten.
- Der aktuelle Fehler ist noch nicht reproduziert.

### Error Message and Logs

Hello All,

I'm trying to set-up Vaultwarden with an argon2id hashed admin password set in Coolify dashboard as per the template.
- The Variable in the template is `SERVICE_PASSWORD_64_ADMIN`
- The argon2id hashed string starts like this: `$argon2id$v=19$m=65540,t=3,p=longstringgoeshere`
- I made sure to double up on `$` so it is parsed correctly when setting the variable in Coolify Dash to: `$$argon2id$$v=19$$m=65540,t=3,p=longstringgoeshere`

After staring the container and looking at defined Environment Variables in terminal by typing `ENV` I see the following 2 variables:
`SERVICE_PASSWORD_64_ADMIN=$argon2id$v=19$m=65540,t=3,p=longstringgoeshere`
and
`ADMIN_TOKEN=2771162argon2id2771162v=192771162m=65540,t=3,p=longstringgoeshere`
Note that the number that replaces the `$` in `ADMIN_TOKEN` changes between reboots.

Naturally when trying to login to the admin panel of Vaultwarden the password that was hashed does not work. From what I understand the container passed the `SERVICE_PASSWORD_64_ADMIN` value to `ADMIN_TOKEN` but something isn't parsing correctly.
- I have tried encasing `SERVICE_PASSWORD_64_ADMIN` value in single and double quotation marks with the same result.
- Any variation of the above with single `$` results in a blank token for both variables.
- Looking at the name of `SERVICE_PASSWORD_64_ADMIN` variable I thought maybe it needs to be Base64 encoded, unfortunately that just results in a plaintext password which is the Base64 string.


P.S. changing Docker Compose from `'ADMIN_TOKEN=${SERVICE_PASSWORD_64_ADMIN}'` to `'ADMIN_TOKEN=$argon2id$v=19$m=65540,t=3,p=longstringgoeshere'` works as expected, but not an ideal solution.

### Steps to Reproduce

1. Install Vaultwarden from template
2. Set Vaultwarden Admin Password (`SERVICE_PASSWORD_64_ADMIN`) in Coolify Dash, by generating an argon2id hash or using any plain password containing an `$`, make sure you escape each `$` with a second one, otherwise it'll fail to parse correctly during container deployment.
3. Go into terminal for the  and type in `ENV`, `ADMIN_TOKEN` will return a malformed value where all `$` is replaced by a set of numbers.
4. Trying to login via Vaultwarden admin url with said password will fail, but will work with the malformed string.
