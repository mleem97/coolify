## Aufarbeitung: CSP- und andere quotierte ENV-Werte verlustfrei serialisieren

**Bereich:** Umgebungsvariablen · **Priorität:** P2 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Ein CSP-Wert mit Leerzeichen sowie einfachen und doppelten Anführungszeichen macht die erzeugte dotenv-Datei ungültig. Der vorgeschlagene Austausch der CSP-Anführungszeichen kann deren Bedeutung verändern und ist keine allgemeine Lösung.

### Reproduktion / Prüfszenario

1. Laravel-Testanwendung mit einem synthetischen CSP-Wert nach dem Originalmuster konfigurieren.
2. Wert über normalen und Literal-Modus als Build- und Runtime-Variable speichern.
3. Erzeugte dotenv-Datei mit dem verwendeten Parser lesen und den Containerwert mit dem Ausgangswert vergleichen.

### Befunde

- Die Fehlermeldung entsteht bei artisan package:discover während des Builds.
- Der Kommentar schlägt umgedrehte Quotes vor, enthält aber keine allgemeine Parserkorrektur.
- EnvironmentVariable und ApplicationDeploymentJob besitzen heute getrennte Auflösungs-/Escaping-Pfade; vorhandene Edge-Case-Tests behandeln andere Interpolationsfälle.

### Umsetzungsschritte

- [ ] Die Serialisierung an der tatsächlich fehlschlagenden Grenze zwischen gespeicherten Werten, Shell und dotenv nachvollziehen.
- [ ] Ein zentral getestetes Escaping für diesen Zielformatpfad verwenden.
- [ ] Den CSP-Wert unverändert erhalten, statt seine gültigen Token-Anführungszeichen umzuschreiben.

### Abnahmekriterien und Regressionstests

- [ ] Der Original-CSP-Wert lässt sich speichern, bauen und im Container identisch lesen.
- [ ] Dollarzeichen, Backslashes, Leerzeichen und beide Quotearten bleiben erhalten.
- [ ] Fehler nennen die betroffene Variable ohne deren vollständigen geheimen Wert.

### Offene Fragen und Risiken

- Ein Fehler im dotenv-Parser der Zielanwendung muss von einem Coolify-Ausgabefehler getrennt werden.

````markdown
### Error Message and Logs

When deploying an application through Coolify, the build fails during the environment parsing step. Although the error message initially looks related to Composer, further investigation shows that Coolify itself struggles to parse a .env variable containing quotes and whitespace (e.g., a Content Security Policy string).

Error message snippet:

```
Generating optimized autoload files
> Illuminate\Foundation\ComposerScripts::postAutoloadDump
> @php artisan package:discover --ansi
The environment file is invalid!
Failed to parse dotenv file. Encountered unexpected whitespace at ["default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline';"].
Script @php artisan package:discover --ansi handling the post-autoload-dump event returned with error code 1
Plugins have been disabled automatically as you are running as root, this may be the cause of the script failure.
See also https://getcomposer.org/root
```
I've tried various methods (e.g., "Is Literal", Build Variable, adding quotes manually) to successfully parse this environment variable, but the build still fails.

### Steps to Reproduce

### Steps to Reproduce
1. Deploy an application using Coolify with a .env variable that includes a CSP directive with quotes, for example:
```
CONTENT_SECURITY_POLICY="default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline';"
```
2. Trigger a build/deployment within Coolify.
3. Observe the error in the logs indicating a failure to parse the .env file due to unexpected whitespace or quotes.
````

````markdown
```
````
