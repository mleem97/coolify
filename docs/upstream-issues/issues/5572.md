## Aufarbeitung: Server-Proxyobjekt im OpenAPI-Schema konkret beschreiben

**Bereich:** API / OpenAPI · **Priorität:** P3 · **Bewertung:** Erweiterung

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Das Server-Schema bezeichnet proxy lediglich als beliebiges object. Dadurch fehlen typisierten Clients Informationen über Typ, Status und weitere öffentlich ausgegebene Felder. Neuere separate Proxy-Endpunkte beseitigen diese Lücke im verschachtelten Serverobjekt nicht automatisch.

### Reproduktion / Prüfszenario

1. Eine repräsentative Serverantwort für Traefik, Caddy und ausgeschalteten Proxy erfassen.
2. Antwort mit dem generierten Server-Schema und dem separaten Proxy-Endpunkt vergleichen.
3. Einen Client gegen das Schema generieren und die Felder typisiert lesen.

### Befunde

- Der Featurewunsch nennt type, status, redirect_enabled, Hashfelder und force_stop.
- app/Models/Server.php enthält weiterhin proxy => type object ohne properties.
- ServerProxyController definiert daneben strukturierte Antworten für eigene Endpunkte.

### Umsetzungsschritte

- [ ] Öffentlich stabile Proxyfelder und optionale Zustände inventarisieren.
- [ ] Ein wiederverwendbares Proxy-Schema mit passenden nullable-/optional-/enum-Angaben definieren.
- [ ] Interne oder sensitive Konfigurationsdaten nicht allein wegen der Schemapflege zusätzlich offenlegen.

### Abnahmekriterien und Regressionstests

- [ ] Generierte Clients können die dokumentierten Felder typisiert lesen.
- [ ] Reale Antworten aller unterstützten Proxyzustände validieren gegen das Schema.
- [ ] Eingeschränkte Tokenantworten und fehlende optionale Felder bleiben korrekt beschrieben.

### Offene Fragen und Risiken

- Nicht jedes schemaless gespeicherte interne Attribut ist automatisch Teil des öffentlichen API-Vertrags.
