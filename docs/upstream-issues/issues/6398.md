## Aufarbeitung: Registry-Anmeldedaten für Non-Root-SSH und Buildserver eindeutig zuordnen

**Bereich:** Registry / SSH-Benutzer / Deployment · **Priorität:** P2 · **Bewertung:** Möglicherweise bereits adressiert

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Ein mit sudo docker login angelegter Root-Zugang ist für einen über einen anderen SSH-Benutzer gestarteten Helper nicht automatisch verfügbar. Der ursprüngliche Bericht beschreibt genau diese Verwechslung. Der heutige Code nutzt bewusst die Docker-Konfiguration des SSH-Benutzers und bietet dafür eine Registry-Verwaltung; spätere Root-Berichte müssen separat reproduziert werden.

### Reproduktion / Prüfszenario

1. Auf einem Testserver als Non-Root-SSH-Benutzer ausschließlich unter Root bei einer privaten Testregistry anmelden und den Fehler dokumentieren.
2. Über Server > Docker Registries denselben Server anmelden und den privaten Pull im Deployment sowie gegebenenfalls auf einem getrennten Buildserver prüfen.
3. Den später gemeldeten Root-Fall mit tatsächlich aufgelöstem HOME, Registryhost, Imagepfad und Zugangstyp getrennt testen.

### Befunde

- Die Meldung beschreibt die Ablage unter /root/.docker/config.json nach sudo docker login, während der Helper das Home des konfigurierten SSH-Benutzers verwendet.
- ApplicationDeploymentJob::prepare_builder_image() mountet heute serverUserHomeDir/.docker/config.json und erklärt bei fehlender Buildserverdatei explizit, warum sudo docker login am falschen Ort landen kann.
- app/Services/DockerRegistryLogins.php liest die Konfiguration aus dem SSH-HOME; die zugehörige Server-Registry-Oberfläche und API sind bereits vorhanden.
- Kommentare vom Juni 2026 berichten zusätzlich Probleme bei Root auf einem von mehreren Servern; das ist kein Beleg für dieselbe Ursache.

### Umsetzungsschritte

- [ ] Den vorgesehenen Registry-Anmeldeweg mit Non-Root-SSH und getrenntem Buildserver end-to-end nachtesten und in der Fehlerhilfe verlinken.
- [ ] Fehlende Konfiguration, falsche Registryadresse, Credential-Helper und abgelaufene Berechtigung getrennt ausweisen.
- [ ] Nur falls der aktuelle kontrollierte Test scheitert, den betroffenen HOME-/DOCKER_CONFIG-Pfad korrigieren; keine Root-Credentials automatisch kopieren.

### Abnahmekriterien und Regressionstests

- [ ] Ein über die Registry-Oberfläche gespeicherter Zugang wird vom zugehörigen Deployment-/Buildserver verwendet.
- [ ] Fehlende oder für einen anderen Benutzer gespeicherte Logins führen zu einer präzisen, geheimnisfreien Meldung.
- [ ] Ein Root- und ein Non-Root-Test decken Pull und Push ab; andere Serverzugänge werden nicht verändert.

### Offene Fragen und Risiken

- Die neue Oberfläche und Fehlerhilfe sind Codebelege, kein Nachweis einer erfolgreichen Laufzeitmigration bestehender Installationen.
- Credential-Helper innerhalb des Helpercontainers und spätere Root-Probleme bleiben gesondert zu prüfen.
- Die Docker-Gruppe oder unnötige Root-Rechte werden nicht als Standardlösung empfohlen.

### Steps to Reproduce

1. Connect a server to Coolify and configure it with a non-root user as described here: https://coolify.io/docs/knowledge-base/server/non-root-user.
2. SSH into that server with the non-root user ("coolify" in my case), run `sudo docker login`, and supply the credentials of a Docker Hub account.
3. Add a new "Docker Image" resource in Coolify and configure a private Docker image.
4. Start the deployment and receive the mentioned error.

### Additional Information

As you can see in my logs (or in the code 😄: https://github.com/coollabsio/coolify/blob/723f14e6f6a84bab744a792c3e628c5e5a3fa308/app/Jobs/ApplicationDeploymentJob.php#L1314), Coolify mounts `/home/coolify/.docker/config.json` ("coolify" is the name of my non-root user here) to `/root/.docker/config.json:ro`.

However, at least by default, Coolify installs "rootful" Docker. Thus, Docker commands need to be run with `sudo` such as `sudo docker login`. This will save the credentials to `/root/.docker/config.json` and not `/home/coolify/.docker/config.json` which is later mounted by the `ApplicationDeploymentJob.php`.

There are to options to fix that:

1. Bind `/root/.docker/config.json` instead of `/home/coolify/.docker/config.json` (or let it select where the credentials could be stored in a slightly smarter way)
2. Add the non-root user to the `docker` group (`sudo usermod -aG docker coolify` for Debian and Debian-based distros) so that `docker login` can be run without `sudo`. This way, the Docker credentials will actually be stored in `/home/coolify/.docker/config.json`. If you prefer this option, I'd suggest to add that information to the "non-root" user documentation at https://coolify.io/docs/knowledge-base/server/non-root-user or add the server's user to the docker group automatically when connecting the server.
