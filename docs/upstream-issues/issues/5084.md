## Aufarbeitung: Erhaltenes Repository im richtigen Preview-Verzeichnis ablegen

**Bereich:** Preview / Dateispeicher · **Priorität:** P2 · **Bewertung:** Möglicherweise bereits adressiert

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Die Preserve-Repository-Option wurde laut genauerem Kommentar angewendet, aber der Checkout lag im Produktionsverzeichnis statt im PR-Verzeichnis. Aktuelle Preview-Pfad- und Compose-Starttests deuten auf spätere Korrekturen hin; der konkrete Post-Deployment-Skriptfall bleibt zu prüfen.

### Reproduktion / Prüfszenario

1. Git-Anwendung mit Preserve Repository und einem synthetischen Post-Deployment-Skript anlegen.
2. Produktion und zwei PR-Vorschauen gleichzeitig deployen.
3. Prüfen, aus welchem Verzeichnis und Commit jedes Skript ausgeführt wird.

### Befunde

- Kommentar 2642011456 korrigiert die ursprüngliche Vermutung: Das Repository liegt im falschen Verzeichnis.
- Kommentar 3946857415 nennt PR 8575 als Fixversuch; Merge-Status wurde hier nicht geprüft.
- tests/Unit/DockerComposePreserveRepositoryStartCommandTest.php und tests/Feature/PreviewFileStoragePathTest.php decken aktuelle Pfadlogik ab.

### Umsetzungsschritte

- [ ] Den ursprünglichen Skriptfall gegen heutige Deploymentverzeichnisse prüfen.
- [ ] Checkout-, Mount- und Hook-Pfade aus einer gemeinsamen Preview-Identität ableiten.
- [ ] Aufräumen nach PR-Schließung auf den PR-eigenen Pfad begrenzen.

### Abnahmekriterien und Regressionstests

- [ ] Jede Vorschau führt ihr eigenes Skript aus ihrem eigenen Commit aus.
- [ ] Produktion wird durch Preview-Checkout und -Cleanup nicht überschrieben.
- [ ] Preserve Repository aus/an führt jeweils zum dokumentierten Dateilebenszyklus.

### Offene Fragen und Risiken

- Vorhandene Tests für Compose-Pfade decken nicht zwingend alle Buildpacks und Hooks ab.
