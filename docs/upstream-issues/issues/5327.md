# Upstream #5327: New-Relic-Logdrain über die gesamte Kette diagnostizierbar machen

[Zur Gesamtübersicht](../README.md)

## Aufarbeitung: New-Relic-Logdrain über die gesamte Kette diagnostizierbar machen

**Bereich:** Logging / Observability · **Priorität:** P2 · **Bewertung:** Reproduktion erforderlich

**Prüfgrundlage:** statische Prüfung von Meldung, abrufbarer Diskussion und Code bei `30335d80866ff3391d899cf4ccb599b696f47b7e`. Keine Laufzeitreproduktion oder Fehlerbehebung in dieser Aufarbeitung.

### Problem und Abgrenzung

Die Diskussion enthält mindestens zwei Fehler: Fluent Bit scheitert an einem ungültigen modify-Set, oder es läuft, erhält aber keine Anwendungslogs. Der aktuelle Code nutzt eine neuere Fluent-Bit-Version und normalisiert Servernamen; historische Logs reichen deshalb nicht als aktueller Fehlernachweis.

### Reproduktion / Prüfszenario

1. Testserver mit New-Relic-Drain und Testanwendung mit aktivierter Logweiterleitung bereitstellen.
2. Konfiguration validieren, Docker-Loggingtreiber prüfen und einen eindeutigen harmlosen Logmarker senden.
3. Marker am Eingang, Ausgang und Ziel verfolgen; danach Dockerfile-App und Compose-Service getrennt testen.

### Befunde

- Kommentar 2732600332 enthält Invalid config for set beim Filterstart.
- Kommentar 3446954271 beschreibt fehlenden fluentd-Loggingblock bei einer Dockerfile-Anwendung.
- StartLogDrain verwendet aktuell Fluent Bit 5.1 und fluentBitValue; ApplicationDeploymentJob und Parser sind weitere Konfigurations-Einstiegspunkte.

### Umsetzungsschritte

- [ ] Konfigurationsfehler, fehlenden Loggingtreiber und abgewiesenen Zielrequest separat anzeigen.
- [ ] Syntax mit Servernamen einschließlich Leerzeichen/leerem Randfall testen.
- [ ] Umschalten des Drains muss bestehende Container bei Bedarf mit neuem Loggingtreiber neu erstellen.

### Abnahmekriterien und Regressionstests

- [ ] Ein Logmarker erscheint einmal mit korrekten Ressourcen-/Serverfeldern im vorgesehenen Ziel.
- [ ] Ungültiger API-Key, falsche Region und unerreichbarer Endpoint erzeugen unterscheidbare Fehler.
- [ ] Deaktivierung und erneute Aktivierung funktionieren ohne manuelle Docker-Bearbeitung.

### Offene Fragen und Risiken

- Ein laufender Fluent-Bit-Container beweist noch keine Logzustellung.
- Reale Providerzugangsdaten und externe Zieltests sind hier nicht vorhanden.

### Kommentar 2888977600 · `hequ`

[Originalkommentar](https://github.com/coollabsio/coolify/issues/5327#issuecomment-2888977600) · 2025-05-18T13:01:22Z

<details>
<summary>Kommentartext</summary>

````markdown
I'm writing these thoughts down here and hopefully this is helpful to someone in the future who tres to configure the log drain with fluentbit.

My problem with fluentbit was, that when I enabled the log drain on my server and on my app, the logs just did not appear in my loki instance and I did not first understand what was going on, since I wasn't very familiar how fluentbit works with docker.

But this is how I eventually got the logs draining.

Enable the log drain on your server and add this input to your fluentbit configuration:

```
[INPUT]
    Name         forward
    Listen       0.0.0.0
    Port         24224
    Tag          docker
```

This starts a fluentbit forwarder input on port 24224, that will listen on your log events. Then enable the log drain on your application. What this does, is that it changes your container's log configuration as follows:

```
docker inspect --format='{{json .HostConfig.LogConfig}}' fc0w8kkso0gksks848c0wgc0-124206086723 | jq .
{
  "Type": "fluentd",
  "Config": {
    "env": "COOLIFY_APP_NAME,COOLIFY_PROJECT_NAME,COOLIFY_SERVER_IP,COOLIFY_ENVIRONMENT_NAME",
    "fluentd-address": "tcp://127.0.0.1:24224",
    "fluentd-async": "true",
    "fluentd-sub-second-precision": "true"
  }
}
```

So after this our application is sending the logs to the forwarder input that is listening the port 24224, and now fluentbit can process your logs. The only thing left is to add the fluentbit output to the service you want.

Check the configuration from: https://docs.fluentbit.io/manual/pipeline/outputs

In case it's helpful my full fluentbit custom configuration for sending the log events to loki (which I self-host) looks like this:

```
[SERVICE]
    Flush        1
    Log_Level    info

[INPUT]
    Name         forward
    Listen       0.0.0.0
    Port         24224
    Tag          docker

[OUTPUT]
    Name         loki
    Match        *
    Host         loki.example.com
    Port         443
    tls          on
    tls.verify   on
    http_user    user
    http_passwd  password
    Labels       job=fluentbit,env=production,server=prod-server,container_name=$CONTAINER_NAME,container_id=$CONTAINER_ID
    Label_Keys   $container_name,$container_id
    net.keepalive   off
    net.keepalive_idle_timeout  30
    ipv6            off
```
````

When deploying an application built from a Dockerfile, Coolify's generated docker-compose file under `/data/coolify/applications/<uuid>/docker-compose.yaml` did not include the logging block (fluentd driver). - Coolify version: 4.0.0-beta.434 (reported in container label)
- Server: Debian/Ubuntu (commands shown run as root)

  - `bootstrap/helpers/parsers.php` and functions that build services/docker-compose (where `data_set($service, 'logging', generate_fluentd_configuration())` happens)
  - Deployment jobs: `app/Jobs/ApplicationDeploymentJob.php` and various `app/Actions/Database/Start*.php` where logging is set for resources.
- Symptoms suggest either:
  - The compose generation path used for Dockerfile-built apps did not include the logging injection (conditional logic skipped), or
  - The resource flag/state used when generating the compose was false/incorrect, or
  - A race/ordering/redeploy behavior where Coolify writes compose without logging, and redeploy doesn't force recreate, leaving existing container on `json-file`.
